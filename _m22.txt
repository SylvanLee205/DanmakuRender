 大部分主播都是下播状态，会提示比较多"

【改动 1：开播图标 🔴 -> 🟢】
🔴 看起来像报错/危险，改成 🟢 更符合"开播"的正面含义。
下播仍是 ⚪（中性）。

【改动 2：修掉启动时的下播通知刷屏（根因分析）】
现象：DMR 每次启动，32 个任务各自去查一次主播状态；
      没开播的任务发一次 liveend 事件 -> onLiveEnd -> _notify_live('end')
      -> 收到 32 条"下播"通知。纯噪音。
      （实测日志：一次启动段里有 64 条"直播已结束"事件）

修法：新增 self._seen_end 标记，区分两种情况：
  - **启动后第一次"直播已结束"** = 初始状态确认，只记录、**不发通知**
  - 之后的"直播已结束" = 说明之前真的开播过，是真下播，正常通知
  - 收到"直播开始"时也把 _seen_end 置 True（开播过，后面下播要通知）

为什么不用"启动后 N 秒内不发通知"的简单方案：
  如果某个主播恰好在启动后几秒内真的下播了，那种方案会漏报。
  用 _seen_end 是按**事件语义**判断，更准确。

【单元测试（按每个任务一个实例的正确模型）】
  场景1 启动瞬间 32 个任务各报一次"已结束"
        -> 共发送 0 条  ✅ 无噪音
  场景2 某主播后来真的开播再下播
        -> 发送 start + end 2 条  ✅ 正常
  场景3 60 秒内重复开播事件
        -> 只发 1 条  ✅ 防抖有效

【真实环境验证】
  重启 DMR 后，本次启动段里"直播已结束"事件 64 条，
  但通知记录只有一条 "[通知] 已发送: DanmakuRender 已启动"。
  -> ✅ 下播刷屏已消除

【保留的设计取舍】
  未开播的主播如果**再次**报"已结束"（例如网络抖动后重连），
  会发一条下播通知。这是有意的：第一次已确认过，第二次说明状态真变了。
  影响很小（防抖 60 秒仍然生效）。
