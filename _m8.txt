新增 CD2 队列健康维护工具 + 记录百度账号级上传限制事故

【新增 tools/cd2_queue_health.py】
  CD2 是 max_upload_threads=1（单线程）。如果一个上传任务永久失败
  （emoji 被拒 / 文件已存在 / 权限被拒），它会**无限重试**，把唯一线程
  占死 -> 后续所有上传被堵住。2026-10-05 那 8427 次重试、10-06 那 3 条
  堵塞任务（54/43/30 次失败）都是这个问题。
  这个工具：读 CD2 日志统计每个文件的失败次数 -> 找出失败超阈值的陈旧
  任务 -> 从 transfer_tasks 删掉（自动停 CD2 + 备份）。
  用法: python tools\cd2_queue_health.py [--clean] [--threshold N]

【事故记录：2026-10-06 百度账号级上传限制】

现象：CD2 日志出现 PermissionDenied("upload file error, unknown error
message")。当天 211 次失败，涉及 4 个任务 13 个文件。
**云端当天收到 0 个文件。**

诊断证据（决定性）：
  - 建目录成功（mkdir OK）、CD2 接受写入成功（create_file OK），
    但上传到百度被拒
  - 传到**全新目录 + 全新文件名**（__torture_test__/a.mp4）一样被拒
  - 冷却 6.8 小时（14:02 -> 20:54）完全无效
  -> 结论：百度侧的账号级限制，不是 CD2 问题、不是路径问题、
     不是文件名问题

时间线：
  02:36~02:59   41 次   （这期间补传还成功过）
  13:00~13:59   40 次   （开始全面失败）
  14~20 点     130 次   （一直失败）

可能诱因：过去几小时的大量上传测试（512MB 限速测试 x2、多次重传、
全新目录测试）叠加看门狗 4 小时反复尝试，触发百度风控。

数据安全：**没有丢失**。所有文件（含当天新的 3 个 vvu）本地都在。

处置：清空 CD2 上传队列停止上传活动。等待更长时间冷却（建议 24-72h），
或考虑切换到 BaiduPCS-Go（不同 API 路径，见
docs/上传方案备选-BaiduPCS-Go迁移手册.md）。

【副产物发现】DMR 的 failed_uploads.json 是空的 —— 因为 rclone 返回
exit=0（CD2 的失败是异步的），DMR 误判成功。这就是"幻影成功"的账号级
版本。已修好的 audit_cloud.py（查 CD2 缓存）能检测到这种问题。
