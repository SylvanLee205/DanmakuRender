# 排查记录：2026-11-02 渲染崩溃事故（同一条断言，三个独立真凶）

> **一句话总结**：蓝羊羊不懒一场渲染 failed，日志只有一条
> `Assertion ((dst_linesize) >= 0 ? (dst_linesize)) >= bytewidth failed at
> libavutil/imgutils.c:351`。我先后"修好"了两次都没修好 —— 因为这条断言背后是
> **三个互不相干**的原因：**无字形字符**、**彩色 emoji 字体**、**源视频损坏帧
> 导致 libass 输出帧 stride 算错**。
>
> **教训：看到同一条报错别认定是同一个原因。必须分层验证 ——
> `-f null`（不编码）跑通说明字幕层没问题，换编码器跑通说明是编码器问题。**

## 二、我错误的排查方向（重点复盘）

| 我的推断 | 依据 | 为什么错 |
|---|---|---|
| 第一次：只是无字形字符 | `failed to find any fallback with glyph 0x3103` 很明确 | **对，但不完整**。清掉 U+3103 后照样崩 |
| GPU 被占用/Arc 驱动问题 | DMR 的 warning 这么写，且 10-20 蓝屏过 0x113 | 是**结果**不是原因；换 libx265 也崩说明与编码器无关 |
| 编码器降级能救 | DMR 设计了 hevc_qsv → libx265 降级 | 根因在 libass 字幕帧，换编码器救不了 |
| PIL 能检测缺字形 | `ImageFont.getbbox()` 有返回值 | 对缺字形返回的是 **.notdef 方框**，尺寸与正常字符一样，区分不出来 |
| `unsafe = color`（彩色字体覆盖的一切） | 逻辑上"在彩色字体里就危险" | **太宽**：彩色字体的 cmap 也含完整 ASCII，会把英文数字全删掉 |
| `unsafe = color - plain`（只有彩色字体有字形） | "别的字体也能渲染就安全" | **太窄**：U+1F1E8 在 SegoeUISymbol 的 cmap 里也有声明，被判安全，但 libass 实际选了 seguiemj |

**最贵的一课**：我修完第一点就认为结案了，没有做"修复后能否真的渲染成功"的
端到端验证，导致同一份日志来回查了三轮。

## 三、决定性测试：分层验证

这是本次排查唯一真正有效的方法。**把"字幕层"和"编码层"分开验**：

| 测试 | 命令要点 | 结果 | 结论 |
|---|---|---|---|
| A 完整渲染（hevc_qsv） | `-c:v hevc_qsv` | 崩（imgutils 断言，5 分钟处） | — |
| B 完整渲染（libx265） | `-c:v libx265` | 崩（段错误 exit 139，21 分钟处） | — |
| C 完整渲染（libx264） | `-c:v libx264` | 崩（stride 640 < 720，50 分钟处） | 三个编码器都崩 |
| D **只跑字幕不编码** | `-f null -` | **400 秒完全不崩** | **字幕层本身没问题** |
| E 无字幕只编码 | 去掉 `-vf subtitles` | 正常出片 | 编码层本身没问题 |
| F 清洗后的 .ass + libx264 | 剔除无字形+彩色字符 | 仍崩（50 分钟处） | **还有第三个真凶** |

**D 和 E 是关键**：它们证明"字幕"和"编码"单看都正常，问题在**两者的结合点** ——
libass 输出的帧本身有问题（stride 640，而视频宽 720），任何编码器都会拒绝。

## 四、三个真凶

### 真凶一：无字形字符（U+3103 注音符号）

弹幕里出现「ㄓ」（U+3103，粉丝打出来的谐音昵称）。Source Han Sans SC
不含 Bopomofo 字形，这台机器上**一个覆盖它的已安装字体都没有**
（微软正黑体 msjh 不在）：

```
fontselect: failed to find any fallback with glyph 0x3103
```

libass 找不到字形 → 输出异常帧 → ffmpeg 断言失败。

### 真凶二：彩色 emoji 字体（Segoe UI Emoji）

清掉 U+3103 后仍在崩，日志变成：

```
Glyph 0x1F1E8 not found, selecting one more font for (Source Han Sans SC, 700, 0)
fontselect: (Source Han Sans SC, 700, 0) -> SegoeUIEmoji, 0, SegoeUIEmoji
Assertion ((dst_linesize) >= 0 ? (dst_linesize)) >= bytewidth failed at imgutils.c:351
```

U+1F1E8 是**国旗区域指示符**（🇨🇳 的前半段）。`seguiemj.ttf` 带 `COLR`/`CPAL`
表，是**彩色字体**，libass 对彩色字形的位图 stride 处理有缺陷，一样触发同一个断言。
🐈 🎂 🌈 ❤ 这些常见 emoji 全在 SegoeUIEmoji 里，同样中招。

### 真凶三：源视频损坏帧 → libass 输出帧 stride 算错

清掉前两类字符后，libx264 撑到 50 分钟才崩，报的是另一条：

```
[libx264] Input picture width (720) is greater than stride (640)
[vost#0:0/libx264] Error submitting video frame to the encoder
Task finished with error code: -542398533
```

定位方法：**同一时段去掉字幕单独渲染，成功了**（ffprobe duration 正常），
说明是字幕+视频的结合问题。而源 ts 那段有大量解码器 concealed errors：

```
[h264] concealing 3152 DC, 3152 AC, 3152 MV errors in B frame
```

链条：

```
源 ts 50-55 分钟有损坏帧（录制时丢包/断流）
  → ffmpeg 解码后该帧尺寸异常
  → libass 叠加输出的帧 stride 按异常尺寸算成 640（视频实际宽 720）
  → libx264 / libx265 / hevc_qsv 全部拒绝（width 720 > stride 640）
```

**绕开方法**：在 `-vf` 里字幕之后加 `scale=720:1280`，强制重新分配缓冲，
stride 就正确了。（`format=yuv420p` 不够 —— 它只转像素格式，不重算 stride。）

## 五、修复

### 1. `DMR/Downloader/Danmaku/glyphs.py`（新增）

开机/首条弹幕时扫一遍系统字体，建两张表，之后每条弹幕过一遍，
把危险字符删掉。扫描结果按字体目录指纹缓存到 `.temp/glyph_coverage.json`，
装新字体会自动重建。

- `covered`：有字形的码位
- `unsafe`：**会回退到彩色字体**的码位

判据是 **`color - primary`**（见下面演进）。`primary` 字体名从
`configs/global.yml` 的 `download_args.live.font` 读，读不到就退化成
"只过滤无字形字符"—— 不会误删 ASCII。

**检测不可用时原样放行**，绝不因为检测失败把弹幕全删了。

### 2. 判据演进（三次才对，别再改回去）

| 判据 | 问题 |
|---|---|
| `color`（彩色字体覆盖的一切） | 太宽。彩色字体的 cmap 通常也含完整 ASCII 区，`sanitize('a,b:c')` 会变成 `''` |
| `color - plain`（只有彩色字体有字形） | 太窄。U+1F1E8/U+1F408 在 SegoeUISymbol 等单色字体的 cmap 里也有声明，被判安全；但 libass 按自己的优先级选，实际选了 seguiemj，照样崩 |
| **`color - primary`**（主字体没有、彩色字体有） | **正确**。主字体有字形就根本不会触发回退，所以只有"主字体缺 + 彩色有"才真正危险 |

### 3. 接入点

`DMR/Downloader/Danmaku/danmaku.py` 在 `dm_available()` **之前**对
`uname` / `content` / `text` 做清洗（清洗发生在写 `.ass` 之前，
所以已经写坏的 `.ass` 不会回溯清洗）。

### 4. 依赖

`requirements.txt` 增加 `fonttools`（纯 Python，无二进制依赖）。
**PIL 不能用** —— `ImageFont.getbbox()` 对缺字形返回 .notdef 方框，
尺寸和正常字符一样，区分不出来。

## 六、顺带做的两件事

### 优雅停止（`main.py` + `tools/stop_dmr.py`）

原来 `stop_dmr.py` 直接 psutil 硬杀，ffmpeg 来不及收尾：正在录的分段停留在
`[正在录制]` 状态、rename 不执行，正在渲染的任务也半途而废。

现在 `stop_dmr.py` 默认走优雅路径：创建 `.temp/graceful_stop_<PID>`，
`main.py` 主循环（每 0.2s 轮询）命中后走 `dmr.stop()`：

```
ffmpeg 收到 'q'（ffmpeg.py 的 communicate('q')）→ 优雅写完当前段
  → segment_callback() 把它改名成正式名
  → 下次启动 reconciler 发现目录里有源视频，自动补派渲染
```

标志文件**带 PID**，绝不会误伤别的实例；DMR 退出时自删，`stop_dmr.py`
也有兜底清理（残留标志会让 DMR 一启动就退出，陷入崩溃循环）。

`--force` 跳过优雅直接硬杀；`--timeout N` 调整等待秒数（默认 180）。

### 孤儿分段登记（`tools/rename_orphans.py`）

录制进程被硬杀时，最后一个分段永远停留在 `[正在录制]<任务>-<时间>-Part%03d.ts`，
`segment_callback` 没跑，状态库里也没有记录 —— 成为"没人管"的孤儿。

而 reconciler 其实**有能力**处理它们（`_promote_intermediate_name()` 会把中间名
按 `output_name` 模板改成正式名，然后 `_dispatch_pending_renders()` 补派渲染），
前提只是**状态库里得有一条记录**。

该工具就是补这条记录：默认预览，`--apply` 才写，写前自动备份 `.db`，
DMR 运行时拒绝写（除非 `--force`），只 INSERT 不更新不删除，
跳过 10 分钟内还在写的文件。

**实测效果**：3 个孤儿全部被 reconciler 自动改名+派发渲染，正是预期的
"下次打开就渲染他们"。

## 七、教训

1. **看到同一条断言别认定是同一个原因。** 这次一条 `imgutils.c:351`
   背后有三个独立故障，我"修好"了两次都没修好。
2. **必须分层验证**：`-f null`（不编码）隔离字幕层，换编码器隔离编码层。
   不做这一步就会一直在一层里打转。
3. **修复后必须端到端验证**（真的渲染出一个能播放的文件），
   不能只验证"字符被删掉了"。
4. **DMR 自己的"原因判断"不可信** —— 它只看了退出码就写"GPU 编码会话被
   其他程序占用"。报错信息要回到 ffmpeg 原始输出去看。
5. **PIL 检测不了缺字形**，只有 fontTools 查 cmap 可靠。
6. **"有字形"不等于"能安全渲染"** —— 还得看那个字形是不是只在彩色字体里。
7. **修完之后才知道源视频本身有损坏帧**（50-55 分钟 concealed errors）。
   这条本来应该更早发现 —— 它和 10-20 断尾人类"录到 31%"是同类问题
   （录制侧丢流），只是这次损坏帧被 `-fflags +discardcorrupt` 掩盖了。

## 八、遗留待办

- **hevc_qsv 本身不稳定**：`-f null` / libx265 均正常，只有 hevc_qsv 崩。
  可能与 10-20 的 Arc 蓝屏 `0x113 VIDEO_DXGKRNL_FATAL_ERROR` 同源。
  DMR 的"qsv 失败降级 libx265"现在能兜住（字幕层修好后降级即可成功），
  但**根因在驱动/QSV，建议更新 Intel Arc 驱动**。
- 已写坏的 `.ass` 不会回溯清洗。要救某一场需对该文件跑一次 `sanitize`
  后重渲（源 `.ts` 通常还在）。蓝羊羊那场的原始 `.ass` 已备份为
  `.ass.bak-20261102`。
