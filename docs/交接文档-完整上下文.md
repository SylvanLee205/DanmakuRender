### ⚠️ 绝对不能做的事

1. **不要把 `configs/` 从 Mod 同步到生产** —— 两边 `auto_upload` 是刻意不同的
   （生产 `True` / Mod `False`）。误同步会让上传**静默停掉**，不报错。
   （已加启动自检 `_verify_pipeline_switches` 来抓这个，但别依赖它）
2. **不要用 `Stop-Process` 直接杀 `main.py`** —— 会留下孤儿 `streamgears` 子进程，
   产生重复录制和孤儿 `[正在录制]` 文件。必须用 `tools\cleanup_duplicate_streamgears.py`
3. **不要启动第二个 DMR 实例** —— 状态库是单例，两个实例会互相踩
4. **不要用 `Start-Process` 直接拉起 bat** —— 用
   `Start-Process -FilePath 'explorer.exe' -ArgumentList '"F:\DanmakuRender_AutoUp\Start_Render.bat"'`
5. **不要用 PowerShell 的 `Get-Content` 不带 `-Encoding UTF8` 读 JSON/日志** ——
   中文会显示成乱码（GBK 误解），我因此误判过两次
6. **不要用 shell heredoc / 字符串拼接去改 Python 源码** —— 引号转义会毁文件。
   用 `edit`/`write` 工具，或写独立的 .py 补丁脚本
7. **`global.ymal`（用户自己的拼写）不要碰** —— 那是用户的私有配置

## 2. 架构：四段流水线

```
┌──────────┐   PipeMessage    ┌────────┐   ┌──────────┐   ┌─────────┐
│downloader│ ───────────────▶ │ render │ ─▶│ uploader │ ─▶│ cleaner │
└──────────┘                  └────────┘   └──────────┘   └─────────┘
   录制                          烧弹幕        传百度网盘      删本地源文件
```

- 插件按 `task['args']` 逐任务创建
- 消息走 `send_queue` / `recv_queue`，事件名如 `livestart` / `livesegment` / `newtask` / `end` / `error`
- 任务配置：`configs/DMR-<主播名>.yml`（**必须以 `DMR-` 开头**，程序靠这个识别）
- 全局配置：`configs/global.yml`（**用户私有，不入 git**）

## 4. 配置语义（最容易踩的坑都在这）

### 4.1 `download_args.live` —— 录制

```yaml
engine: auto            # auto | ffmpeg | streamgears | streamlink | pyrequests
dm_filter:
  dm_type: ['danmaku', 'gift']   # 只收弹幕+礼物（过滤进场/点赞）
output_name: '{STREAMER.NAME}-{CTIME.YEAR}年{CTIME.MONTH:02d}月...'
```

**`engine` 选择逻辑**（`stream_downloader.py:420`）：
- B站：`.m3u8` → ffmpeg；否则 streamgears
- 抖音/斗鱼/虎牙/CC：`.m3u8` → ffmpeg；否则 **streamgears**（抖音的 flv 走这里）
- 其他 → streamlink

### 4.2 `render_args.dmrender` —— 渲染

```yaml
vencoder: hevc_qsv
vencoder_args: ["-preset","medium","-global_quality:v","30","-tag:v","hvc1","-movflags","+faststart"]
aencoder: libopus
aencoder_args: ["-b:a","96k","-vbr:a","on"]
gop_multiplier: 4        # ★ 单位是"秒"！4 = 每 4 秒一个关键帧 → -g = round(帧率×4)
gop_default_fps: 24      # 探测不到帧率时的兜底（实测抖音 20~22fps）
skip_upload_rule:
  enabled: true
  skip_landscape: true          # 跳过横屏
  skip_require_landscape: true  # 横屏是必选前置条件
  skip_bitrate_kbps: 2500
  skip_fps: 40
  skip_min_matches: 1
```

**GOP 要点**：`gop_multiplier` 是**秒**不是"倍帧率"。22fps × 4 = `-g 88`。
设 `~` 表示不干预、用编码器默认。**别填 80**（会变成每 14.5 秒一个关键帧）。

### 4.3 `upload_args_task_default` —— 上传

```yaml
dm_video:
  - target: rclone
    realtime: true        # ★★★ 必须 true ★★★ 否则 _check_for_upload 不会实时触发
    command: ['rclone','copy','{PATH}','cd2:百度网盘/DMR录播/{TASKNAME}',
              '--retries','5','--low-level-retries','10','--transfers','1']
```

**没有 `src_video` 上传规则** —— 源视频从不上传。这决定了清理逻辑（见下）。

### 4.4 `clean_args_task_default` —— 清理（**2026-10-18 大修**）

```yaml
dm_video:                # ★ 必须用 dm_video 作键（原因见下）
  method: delete
  delay: 172800          # 48 小时后悔期
  w_srcfile: True        # 连带删源视频
  w_dmfile: False        # ★★ 弹幕版本身不删（本仓库新增的开关）
  w_srcpre: True
```

**为什么必须用 `dm_video` 作键**：
`_check_for_clean()` 的触发门槛是 `info['status'] == 'uploaded'`。
只有 `dm_video` 会被上传（`src_video` 没有上传规则，永远停在 `recorded`），
所以清理只能从 `dm_video` 入口触发。

**`w_dmfile` 是本仓库新增的开关**（上游没有）：
- 默认 `True` = 老行为（弹幕版和源视频一起删）
- `False` = 只删源文件，弹幕版保留本地

**官方支持的其他键名**（`.split('+')` 匹配）：
`src_video` / `dm_video` / `src_video_pre` / `all` / `src_video+dm_video`

### 4.5 `state` / `recovery` —— 状态库与恢复

```yaml
state:
  db_path: logs/dmr_state.db
recovery:
  on_interrupted_file: ask    # ask / keep / discard
  resume: true
```

**状态机**（`DMR/state/enums.py`）：
```
planned → recording → recorded → rendering → rendered → uploading → uploaded → cleaned
                                                        ↘ skipped
                    （mising / interrupted 为异常态）
```
- `RESUMABLE_STATES = {RECORDED, RENDERED}` —— 只有这两个会在启动时被重新驱动
- `SKIPPED` 不可恢复（写进库就不会再重跑）
- `UPLOADED` / `CLEANED` 永不重跑（防重复投稿）

## 7. 失败模式分类学（找 bug 的方法论）

在这个项目里踩过的 bug **只有三类**，遇到"功能没生效"先按这个顺序排查：

| 类型 | 表现 | 检测方法 |
|---|---|---|
| **A. 名字用了但拿不到** | `NameError: name 'xxx' is not defined` | `tools\check_critical_names.py`、`tools\deep_name_scan.py` |
| **B. 方法定义了但没人调用** | 配置写了、日志没报错、就是不生效 | `tools\feature_audit.py` 的 **D 段接线检查** |
| **C. 依赖注入了但没透传** | `AttributeError: 'X' object has no attribute 'y'` | **单元测试**（静态工具抓不到） |

> **教训**：437 个单元测试是**最有效的回归信号**。它抓到了 `Downloader.state_repo`，
> 而三个静态审计工具全部漏掉。每次改完代码必须跑：
> `python -m unittest discover -s unit_tests -t .` → 期望 `Ran 437 tests, OK (expected failures=5)`

## 9. 操作手册

### 9.1 安全重启（**唯一推荐方式**）

```powershell
cd F:\DanmakuRender_AutoUp
# 先确认没有录制活动
Get-ChildItem 直播回放 -Recurse -File -Filter *.flv.part
# 执行（内部会：停守护 → 停 DMR → 停 streamgears → 等 >2 分钟让 recover_part 接管 → 重启）
.venv\Scripts\python.exe tools\cleanup_duplicate_streamgears.py
```

**为什么不能直接杀**：`main.py` 被杀后 `streamgears_wrapper` 子进程会活下来，
导致同一主播两个录制器 + 孤儿 `[正在录制]` 文件。已踩过两次。

### 9.2 部署（Mod → 生产）

```powershell
robocopy 'F:\DanmakuRender_Mod' 'F:\DanmakuRender_AutoUp' /E /XO `
  /XD .venv configs logs 直播回放 .temp .git __pycache__ login_info `
  /XF "global.ymal" "global.yaml" /NJH /NJS /NDL /NC /NS
```

**⚠️ 永远排除 `configs`** —— 那是"皇冠上的宝石"，两边刻意不同。

`configs` 单独处理：
```powershell
Copy-Item 'configs\global.yml' 'F:\DanmakuRender_Mod\configs\global.yml' -Force
```

| **19 个 `skipped` 源视频** | 命中跳过规则（横屏/高码率），**按设计保留本地**，不会被清 |
| **状态库会回收场次** | 全部产物终态后场次被回收，历史记录消失。`--keep` 无效，属上游设计 |
| **`failed_renders.json` 乱码** | **误报**，文件本身正确（UTF-8）。是 PowerShell `Get-Content` 不带 `-Encoding UTF8` 的读数假象 |

## 10.5 两个重要发现（2026-10-18 深夜，来自用户实证）

### 发现 1：`.flv.part` 体积不能用来判断录制是否停滞 🔴

**用户多次实证 + 2026-10-18 硬数据**：
- `.flv.part` 的体积会长时间一动不动
- 但弹幕 `.ass` 在正常增长（说明直播还在、下载器也在收数据）
- **一结束程序，`.part` 体积突然从几 KB 跳到上百 MB**

**实测铁证（2026-10-18 断尾人类）**：
```
看到的:  [正在录制]...flv.part    495.9 MB   冻结 74 分钟（21:38:16 → 22:52:02）
结束时:  断尾的人类不会喵-...20点56分.mkv   1,351.6 MB   ← 涨了 855 MB
时长:    10,748 秒（约 3 小时）
```
**855 MB 数据一直缓存在内存里。** 如果按"5 分钟不动就重连"的看门狗处理，
这个健康录制 3 小时的任务会在第 5 分钟被杀掉。

**结论**：`biliup` 内部有较大的**内存缓冲**，落盘是成块/延迟的。
`os.path.getsize()` 和 `st_mtime` **完全不能反映"是否还在收数据"**。

**⚠️ 我曾经据此加过一个"5 分钟不增长就判停滞并重连"的看门狗，被用户纠正后撤销。**
那种判据会把**健康录制误判成停滞并 kill**，造成真实数据丢失 ——
比"漏检停滞"严重得多。代码里已留下注释说明为什么不能这么做。

**正确的存活信号（可靠性排序）**：
1. 子进程是否还活着（`poll()`）—— 最可靠
2. **下载器自身输出的日志**是否还在产生新行 —— DMR 的 ffmpeg 引擎就是这么做的
3. 弹幕 `.ass` 是否还在增长 —— 只能作旁证（不同线程写的）

### 发现 2：`output_format: mkv` 是**假的**，真实容器是 FLV 🔴

**实测**：
```
文件名: 断尾的人类不会喵-2026年10月18日19点56分.mkv
ffprobe: format_name=flv  format_long_name=FLV (Flash Video)
```

**原因**：`engine: streamgears` 的 wrapper **完全不看 `output_format`**，
只按传入的文件名写 FLV，结束时把 `.flv.part` 改名成 `.mkv`。
**扩展名和内容不一致。**

**影响**：
- ffmpeg 系工具能正常读（按内容识别），所以录制/渲染没坏
- 但播放器/网盘预览/部分上传器可能困惑
- **更重要的是：FLV 容器在异常中断时容易损坏**（需要正确关闭才完整）

**DouyinLiveRecorder（最成熟的抖音录制项目）明确建议**：
> 为避免手动中断或者异常中断导致录制的视频文件损坏的情况，**推荐使用 `ts` 格式保存**。

**所以推荐**：把 `output_format` 改成 `ts`，并切换到 `engine: ffmpeg`
（ffmpeg 引擎里 `output_format` 是**真生效**的，它决定写入容器）。

| 引擎 | `output_format` 是否生效 | 真实容器 |
|---|---|---|
| `streamgears` | ❌ 不生效（只当文件名后缀） | **永远是 FLV** |
| `ffmpeg` | ✅ 生效（决定 ffmpeg 输出格式） | 按配置（ts/mkv/mp4） |

## 10.6 第三个重要发现：QSV 编码会话争抢会导致渲染残缺 🔴

### 现象

渲染失败，报：
```
[hevc_qsv] Invalid FrameType:0.
Error submitting video frame to the encoder
Task finished with error code: -1094995529 (Invalid data found when processing input)
```
留下 **17% / 27% / 42% / 56%** 不等的残缺产物，而且**三次失败点各不相同**。

### 根因（2026-10-18 深夜确认）

用户在后台跑**双路批量渲染脚本**（两个 `ffmpeg ... -c:v hevc_qsv` 进程），
占满了 Intel Arc A380 的 QSV 编码会话。DMR 的渲染拿不到会话就失败。

### 关键验证

| 测试 | 结果 |
|---|---|
| 源文件完整解码（`ffmpeg -f null -`） | **0 致命错误**（539 条都是 DTS 警告） |
| GPU 空闲时 4 种编码方案（含纯 qsv）跑 90 秒 | **全部成功** |
| GPU 被占用时完整渲染 | **失败**（且失败点随机） |

**结论：这是资源争抢，不是素材损坏，也不是 DMR 的 bug。**

### 已实现的修法：硬件编码失败自动降级

`DMR/Render/dmrender.py:render_one` 里，硬件编码器
（`*_qsv` / `*_nvenc` / `*_vaapi` / `*_amf` / `*_videotoolbox`）
渲染失败时，**自动用软件编码器重试一次**：

```yaml
# global.yml → render_args.dmrender
fallback_vencoder: libx265                                  # 置空可关闭降级
fallback_vencoder_args: ['-preset','veryfast','-crf','30','-tag:v','hvc1']
```

**行为**：
- 只重试一次，不循环
- 重试前删掉残缺产物（避免 ffmpeg 因文件已存在而拒绝覆盖）
- 日志会明确说明"GPU 编码会话被占用"

**实测**：断尾人类 19:56 分段 —— QSV 跑 4:35 失败 → 自动降级 libx265 →
31 分钟完成 382.3 MB，源 3792s → 产物 3603s（95%），上传成功。

**注意**：QSV 争抢是**间歇性**的。同一晚 23:08，DMR 渲染 3 小时那个分段时
GPU 恰好有空，QSV 直接成功，没触发降级。所以降级是安全网，不是每次都用。

### 运维建议

跑批量渲染/转码脚本时，最好错开 DMR 的渲染高峰，
或者给批量脚本也加降级，避免互相争抢。降级后速度约慢 2 倍
（实测 90 秒片段：QSV 12s vs libx265 veryfast 26s）。

## 11. stream-gears 对抖音的支持 —— 评估与建议

### 结论：`stream_gears` 确实是 B站优先，对抖音只能算"能用但不稳"

**`stream-gears` 是 `biliup-rs` 的 Python 绑定**（Rust 实现），原本为 B站设计。

### 实测问题（本项目日志统计）

| 问题 | 次数 | 根因 |
|---|---|---|
| `pyo3_runtime.PanicException: overflow when subtracting durations` | 42（单日） | 流时间戳错乱（DTS 跳回 0），Rust 层做减法溢出 |
| `Stream-gears 异常退出` | 1751（历史累计） | 同上 + CDN 断连 |
| `Non-monotonous DTS` | 频繁 | 抖音 flv 流常见现象 |

**关键缺点**：
1. `stream_gears.download()` 是"单次调用"——连接一断就返回、进程退出，
   重连靠外层 DMR 的退避循环
2. **遇到坏时间戳直接 panic**（Rust 不做容错），而不是跳过坏帧继续
3. **没有可靠的停滞检测**——文件体积不可信（见 10.5 发现 1），
   而它自身也不会在"连着但没数据"时主动退出

### ⭐ 对照：DMR 的 ffmpeg 引擎**已经自带正确的停滞检测**

```python
# DMR/Downloader/ffmpeg.py:245
if self._received_lines == window_baseline:
    raise RuntimeError(f'{self.taskname} 15 秒内未收到任何 ffmpeg 输出, 即将重试.')
```

它用 **ffmpeg 自身的 stdout 输出量**判断存活 —— 这是可靠信号，
而且 15 秒就能发现停滞（streamgears 完全没有这个能力）。

### ⭐ 对照：DouyinLiveRecorder 是怎么做的（用户亲测"极为稳定"）

来自其 README（[ihmily/DouyinLiveRecorder](https://github.com/ihmily/DouyinLiveRecorder)）：

> 一款简易的可循环值守的直播录制工具，**基于 FFmpeg 实现多平台直播源录制**

**架构**：
```
spider.py   → 获取直播数据
stream.py   → 解析直播流地址
ab_sign.py  → 生成抖音签名 token（对应 DMR 的 abogus.py）
ffmpeg.exe  → 真正录制
```

**对我们最有价值的三条经验**：
1. **用 ffmpeg 录制**，不用 Rust/自研下载器 → 遇到坏流不 panic，坏帧跳过
2. **推荐 `ts` 容器** → 异常中断不易损坏（FLV/MP4 需要正确收尾）
3. **跟进平台变化很勤**（更新日志里多次"修复抖音风控无法获取数据"）
   → 它的抖音解析逻辑比 DMR 更新快

**但它是纯录制器**：没有弹幕烧入视频、没有上传、没有清理流水线。
所以不能替代 DMR，只能作为"下载引擎思路"和"抖音解析"的参考。

### 推荐方案（按优先级）

#### ✅ 方案 1：把抖音的下载引擎换成 `ffmpeg`（最推荐，改动最小）

DMR **原生支持** `engine: ffmpeg`：

```yaml
# configs/global.yml → download_args.live
engine: ffmpeg        # 原来 auto（= streamgears）
```

**理由**：
- ffmpeg 对坏时间戳有成熟的容错（`-fflags +discardcorrupt+genpts` 已在渲染侧用了）
- **不会 panic**，坏帧跳过继续录
- 已经装了、不需要新依赖
- DMR 的 ffmpeg 下载器已支持 flv（B站 hls 也走它）

**风险**：ffmpeg 录制 flv 的分段/断流处理与 streamgears 不同，需要实测对比。
**建议**：先给**一个**任务（比如灰蒙蒙，它最容易坏流）单独试 `engine: ffmpeg`，
跑 2-3 场确认分段正常、无丢帧，再全局切换。

#### ⚠️ 方案 2：保留 streamgears，但加"坏流熔断"（折中）

如果换 engine 有顾虑，可以加逻辑：同一任务连续 N 次 panic 后，
临时切换到 ffmpeg，直播结束后恢复。改动量中等。

#### ❌ 方案 3：换整个项目（不推荐）

搜到的抖音相关项目：

| 项目 | 定位 | 能否替代 DMR |
|---|---|---|
| [ihmily/DouyinLiveRecorder](https://github.com/ihmily/DouyinLiveRecorder) | 40+ 平台录制，抖音起家，最活跃 | ❌ **只录制**，不渲染弹幕、不上传、不清理 |
| [SRLib-hoby/DouyinLiveRecorderDanmu](https://github.com/SRLib-hoby/DouyinLiveRecorderDanmu) | 抖音专用，可录弹幕，GUI+CLI，免 cookie/免 selenium | ❌ 同上，只到"录+收弹幕" |
| [bililive-go](https://baike.baidu.com/item/bililive-go/68156767) | 多平台录制 | ❌ 只录制 |

**核心判断**：
> **没有任何流行开源项目同时做「录制 + 弹幕烧进视频 + 上传网盘 + 自动清理」。**
> DMR 的不可替代价值就在这后半段流水线。

所以正确做法是**换掉 DMR 里最弱的一环（下载引擎），而不是换掉整个 DMR**。

#### 💡 方案 4：DouyinLiveRecorder 作为"兜底录制器"（可选补充）

`DouyinLiveRecorder` 的抖音解析比 DMR 更新快（它是抖音起家，跟进平台变化积极）。
可以只把它当**备用录制器**：DMR 连续失败时由它补录，之后手动喂给 DMR 渲染。
但这个集成成本高，除非 streamgears 问题严重到不可接受，否则不建议。

### 关于 B站 / 快手（用户说概率不高）

- **B站**：DMR 支持最好（streamgears 就是为它写的，`.m3u8` 会自动走 ffmpeg）。
  切换 `engine: ffmpeg` 对 B站 hls 无影响。
- **快手**：DMR 走 streamlink 分支，`streamlink` 有快手插件。
  如果将来要录快手，建议单独给那个任务配 `engine: streamlink`。

## 14. 下一个接手者的 Checklist

接手时按顺序做：

1. **读本文档第 1 节**（路径）和第 4 节（配置语义）—— 最容易出错的地方
2. **确认生产在跑**：
   ```powershell
   Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where-Object { $_.CommandLine -like '*main.py*' }
   Get-ChildItem F:\DanmakuRender_AutoUp\logs -Filter 'DMR-2026*.log' | Sort-Object LastWriteTime -Descending | Select-Object -First 1
   ```
3. **看最新日志的 ERROR 数**（应为 0）
4. **跑一次回归**：`tools\regression_check.py`
5. **确认清理规则**：`clean_args_task_default` 必须是 `dm_video` 键 + `w_dmfile: False`
6. **确认 `auto_upload` 是 True**（33 个任务都该是 True）
7. **不要碰 `configs/global.yml` 以外的配置**；改它之前先 `backup_configs.py snapshot`

### 三个最容易犯的错

1. **以为 `src_video` 从 `uploaded` 状态开始清理** → 它永远不会，必须从 `dm_video` 触发
2. **以为 `gop_multiplier` 是倍帧率** → 它是**秒**
3. **以为弹幕版可以删** → **用户明确要求永久保留本地**
