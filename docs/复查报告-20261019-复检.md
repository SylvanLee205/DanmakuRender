## 二、本轮新发现

### 🔴 N1 渲染超时被固定成 600 秒 —— 会杀掉正常的长渲染

**位置**：`DMR/Render/ffmpeg.py:44`

```python
_timeout = max(600.0, float(getattr(self, "src_duration", 0) or 0) * 10 + 600)
```

`src_duration` **全仓只出现这一处**（没有任何地方赋值），所以 `getattr` 永远拿到 0，
超时恒为 **600 秒**。原意"按源时长放宽"从未生效。

**实测数据（10-17～10-18 共 72 次渲染完成）**：

```
中位数 46 秒   最长 964 秒   超过 600 秒的 2 次
16.1 分钟 | 断尾的人类不会喵-2026年10月18日20点56分.mkv   ← 3 小时分段，QSV
15.3 分钟 | 2026-10-17 23:35 那一段
```

按当前代码，这两次都会在 10 分钟时被 `kill()` → 返回 -1 → 渲染失败。
更糟的是失败后还会走 `hw_retry`（2 次 × 60 秒间隔，每次仍然给 600 秒），
再降级 libx265（历史实测 **31 分钟**完成），**每一次都会被同一个 600 秒砍掉**。
最终结果：长分段彻底没有弹幕版，而源视频还在（因为 `failed` 不触发清理）。

**修法（二选一，推荐 A）**
- A. 在 `DmRender.render_helper()` 里把源时长交给渲染器，让公式真正生效：
  ```python
  try:
      self.raw_ffmpeg.src_duration = float(getattr(video_info, 'duration', 0) or 0) \
          or FFprobe.get_duration(video)
  except Exception:
      self.raw_ffmpeg.src_duration = 0
  ```
  注意转码路径用的是 `Transcoder`，同样需要设置。
- B. 至少把下限从 600 秒提到 `max(3600, ...)`，覆盖 3 小时分段 + 软编码降级。

> 我认为这是本轮**唯一会立刻造成数据/产物损失**的改动，建议优先修。

### 🟠 N3 待删清单的清理写法会提前丢掉"已到期但还没删完"的条目

**位置**：`DMR/Cleaner/__init__.py` 的 `_rearm_pending()` 末尾

```python
if len(alive) + len(overdue) != len(entries):
    self._journal_save(alive)      # ← 只写了 alive，overdue 被一起抹掉
```

`overdue` 只是**提交**给线程池，删除动作还没执行。此时把清单写成 `alive`，
等于把"到期项"从权威记录里删了；若进程在这之后、删除完成之前退出（又一次重启/崩溃），
该文件**再也没有任何记录**，回到 R1 修复前的状态。

**已复现**（把 `submit` 换成空实现，模拟"已提交未执行"）：

```
提交删除后、删除尚未执行时，清单剩余: ['3']
overdue.mkv 仍在磁盘: True
=> 已到期待删项是否从清单中消失: True
```

**修法**：`self._journal_save(alive + overdue)`（到期项由 `_clean_subprocess` 成功后的
`_journal_remove` 移除；文件已消失的仍由开头的 `pairs` 过滤剔除，不会无限循环）。
