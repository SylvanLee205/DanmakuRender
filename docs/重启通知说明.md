## 二、⚠️ 换行格式（关键，实测踩坑）

**Server酱³ 按 Markdown 解析 `desp`。** 实测三种写法：

| 写法 | 结果 |
|---|---|
| 纯 `\n` | ❌ 手机列表页看着像换行，**点进"原文"就没了** |
| `<br>` | ❌ **原样显示成 `<br>` 文本** |
| HTML 标签如 `<b>` | ❌ 原样显示成 `<b>粗体</b>` |
| **两空格 + `\n`** | ✅ **正确换行**（Markdown 硬换行语法） |

所以 `DMR/notify.py` 里统一用：
```python
_NL = '  \n'        # 两个空格 + 换行
def _join(lines):
    return _NL.join(str(x) for x in lines)
```

## 三、内容设计取舍（按用户反馈调整）

| 字段 | 决定 | 理由 |
|---|---|---|
| 启动时间 | **删** | 通知本身自带时间，重复没意义 |
| 近 24h 录制 | **删** | 启动时看它没有行动价值 |
| 正在录制 | **删** | 启动瞬间必然还没开录，只会显示"暂无" |
| 监听 N 个主播 | **改成列出名字** | 光说"32 个"不知道是谁。改成显示实际名单 |
| 云端通道 CD2 | **留** | 启动时最该确认的就是"上传通道通不通" —— 历史上最常出问题的一环 |
| 磁盘剩余 | **新增** | 快满了会导致录制失败，是真实风险（阈值 30 GB 告警） |
| 频繁重启告警 | **留** | 崩溃循环时能立刻察觉 |

**"正在录制"的真正归宿**：它不该出现在启动通知里，而该在**开播/下播时**通知 ——
那时信息才是准的。所以新增了开播/下播通知（见上）。

## 四、开播/下播通知的实现

在 `DMR/Task/liveevents.py`：
```python
def defaultEvent(self, message):
    ...
    if '直播开始' in str(message.msg):
        self._notify_live('start')      # 开播 -> 通知

def onLiveEnd(self, message):
    ...
    self._notify_live('end')            # 下播 -> 通知
```

**特性**：
1. **后台线程发送** —— 不阻塞事件处理，不影响录制
2. **60 秒防抖** —— 同一个任务的同一种事件 60 秒内只发一次
   （网络抖动可能导致重复的 livestart 事件，防抖避免刷爆手机）
3. **异常静默** —— 通知失败不影响主流程

## 五、架构：谁发通知

```
DMR 启动成功
  └─ main.py 起后台线程
       └─ tools/gen_restart_notify.py
            ├─ build()  收集：主播名单/版本/CD2状态/磁盘/重启次数
            └─ DMR/notify.py send()  → 写 UTF-8 文件 → curl 发送

主播开播/下播
  └─ DMR/Task/liveevents.py
       └─ DMR/notify.py send()  → 同上
```

**为什么不由 bat 发**（旧做法已废弃）：
- bat 在启动**前**发，只能说"我要启动了"；DMR 启动失败时会**误报"已复活"**
- DMR 在启动**成功后**发，能带真实的任务名单和状态

**为什么中文不写进 bat**（血的教训）：
```
cmd.exe 按系统代码页(936/GBK)解析 bat，chcp 65001 还没生效就已读完文件。
UTF-8 中文会被当 GBK → 乱码 → 命令破碎 → 无限刷屏
    '_URL" >nul' 不是内部或外部命令...
（2026-10-07 实际发生，刷了几百行）
```
现在 bat 保持**纯 ASCII**（0 个非 ASCII 字节），中文一律走 UTF-8 文件。

## 六、频繁重启检测

```
FLAP_WINDOW    = 3600   # 1 小时窗口
FLAP_THRESHOLD = 3      # 超过 3 次告警
MIN_COUNT_GAP  = 600    # 距上次计数不足 10 分钟不重复计数
```

`MIN_COUNT_GAP` 防误报（调试时短时间重启多次）：
```
连续重启 3 次（间隔 <10min） -> 只计 1 次  ✅
隔 11 分钟再重启            -> 正确 +1    ✅
```
真正的崩溃循环间隔（10 秒重试）远小于 10 分钟，仍能识别。
