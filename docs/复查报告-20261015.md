| 手段 | 工具 | 针对的盲区 |

## 二、发现并修复的问题（3 个）

### 🔴 1. `Downloader` 基类缺 `state_repo`（单元测试抓到）

```
ERROR: test_downloader_plugin_receives_state_repo
    self.assertIs(downloader.state_repo, dmr.state_repo)
    AttributeError: 'Downloader' object has no attribute 'state_repo'
```

合并上游时 `DMR/Downloader/__init__.py` 漏了两处：

```python
# a) __init__ 没有 state_repo 参数
def __init__(self, pipe, state_repo=None, **kwargs):   # ← 我们缺 state_repo
    self.state_repo = state_repo                        # ← 也缺这行

# b) newtask() 没有把 state_repo 透传给具体下载任务
if self.state_repo is not None:
    config = {**config, 'state_repo': self.state_repo}  # ← 我们缺这段
```

**影响**：`StreamDownloadTask` 拿不到状态库，"录制分段登记到状态库"是哑的。
之所以线上没表现出明显故障 —— 上游在 `stream_downloader.py` 里还有一层
模块级 `_STATE_REPO` 兜底，而 `DMR/__init__.py` 的 `set_state_repo()`
那条路是通的。**所以只有单测抓到了。**

已按上游补齐。验证：`Ran 4 tests OK`。

### 🔴 2. 0 字节产物保险闸丢失（`feature_audit.py` 抓到）

我当初把 `dmrender.py` 取上游版时，加回了 GOP 和编码器参数校验，
但漏了"产物为 0 字节则判失败并删除"这道保险 —— 那正是 2026-10-05
事故（上传空文件 + 清理删掉源视频）的产物。

**核查结论：上游已从根因修掉了这个问题**：

```python
# DMR/Render/ffmpeg.py
# ⚠️ 必须读退出码！原版把 wait() 的返回值丢了，改成靠日志里有没有
# "video:" 来猜成功 —— 只要 ffmpeg 打印过 Stream mapping 段再失败，
# 就被判成成功，0 字节/残缺产物继续往下游走
returncode = self.render_proc.wait()
if returncode == 0: return True, info
```

实测两种必然失败的输入（无效编码器 / 无效滤镜），**都正确判为失败**。

不过保险成本极低、收益很高（0 字节产物一旦下发不可恢复），
所以**叠加保留**，并加了注释说明这是第二道闸。实测：
- 伪造"成功 + 0 字节" → 产物被删除、判失败 ✅
- 真实渲染 → 18.64 MB 正常，未误伤 ✅

## 四、经验教训（已固化为工具/流程）

| 教训 | 固化方式 |
|---|---|
| 合并上游不能只看冲突列表 | `audit_undefined_names.py` 自动对比所有 `__init__.py` 导出差异 |
| `import *` 让静态检查失效 | `deep_name_scan.py` 递归展开 `import *` 再查 |
| 函数体内的名字 import 期不报错 | `check_critical_names.py` + 接入启动流程 |
| 重启必须处理子进程 | `cleanup_duplicate_streamgears.py` 按序停守护→DMR→**streamgears** |
| robocopy `/XF "_*.py"` 会误伤 `__init__.py` | 改用精确模式（见上） |
| **单元测试是最有效的回归手段** | 每次改完必跑 437 个测试 |

> 最后一条是本次复查最大的收获：`Downloader.state_repo` 这个漏洞，
> 我的三种静态工具都没发现，**是单元测试抓到的**。
