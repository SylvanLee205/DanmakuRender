# 排查记录：2026-10-06 上传失败事故（根因：路由器限速设错单位）

> **一句话总结**：路由器限速**填成了 4 Mbps**（应为 35 Mbps），
> 上行被掐到 0.5 MB/s，导致大文件传百度超时被拒 `PermissionDenied`。
> 我花了半天往"百度封号""CD2 不稳"方向排查，**全都是错的**。
> **教训：上传出问题，第一步先测真实出网带宽。**

---

## 一、事故现象

2026-10-06 下午起，CD2（CloudDrive2）上传百度网盘持续失败：

```
ERROR cloudapi::transfers: upload error for /百度网盘/DMR录播/vvu/vvu-...mp4:
PermissionDenied("upload file error, unknown error message: ")
```

- 当天累计 **211 次**失败，涉及 **4 个任务 13 个文件**
- **云端当天收到 0 个文件**
- 受影响的是 100MB~350MB 的**大文件**

---

## 二、错误的排查方向（重点复盘）

我按"账号/服务问题"的思路排查，**方向全错**：

| 我的推断 | 依据 | 为什么错 |
|---|---|---|
| 百度账号被限制 | 换全新目录+全新文件名也被拒 | 与账号无关，是速度问题 |
| 百度按内容限制视频上传 | 小 .bin 成功、大 .mp4 失败 | 变量没控制住：**小**和大才是差异，不是类型 |
| CD2 单线程队列堵塞 | 3 条任务失败 54/43/30 次占死线程 | 堵塞是**结果**（上传超时），不是原因 |
| 需要换 BaiduPCS-Go | 想换不同 API 路径 | 换哪个都得走这条上行带宽 |
| 需要换 CD2 核心服务版 | 觉得应用版不稳 | 瓶颈在运营商/路由器，与 CD2 实现无关 |
| 冷却 6.8 小时会恢复 | 以为是限流 | 限速一直在，冷却再久也没用 |

**直到用户说"我路由器限速限错了，限成 4Mbps 了"** —— 一切才对上。

## 三、决定性测试（正确做法）

**控制变量**：全部切成**同样 2MB**，只变内容/扩展名：

```
1 纯数据 .bin    ✅ 成功
2 真视频 .mp4    ✅ 成功      ← 关键！视频其实能传
3 真视频 .bin    ✅ 成功
4 纯数据 .mp4    ✅ 成功
5 真视频 .txt    ✅ 成功
```

**全部成功** → 说明**类型无关**。之前的"小 .bin 成功、大 .mp4 失败"
真正的差异是 **文件大小**（1MB vs 350MB），不是我推断的类型。

而"大小"为什么重要？因为**带宽被限到 0.5 MB/s**：
- 1MB 文件 → 2 秒传完 → 成功
- 350MB 文件 → 要传 12 分钟 → **超时被百度拒绝**

## 四、根因

```
路由器限速填成了 4 Mbps   （本意可能是 4 MB/s，或者填错字段）
    ↓
实际上行 0.5 MB/s（用户宽带标称 5-6 MB/s）
    ↓
CD2 上传大文件到百度需要 10+ 分钟
    ↓
百度侧接收超时/连接中断 → 返回 PermissionDenied
```

**单位换算**：
```
4 Mbps  = 0.5 MB/s      ← 错误设置
35 Mbps = 4.4 MB/s      ← 修正后
```

## 五、正确的排查顺序（下次照这个来）

**上传失败，先按这个顺序查，不要跳步：**

1. **测真实出网带宽**（第一步！）
   ```powershell
   # 用 curl 传 16MB 到测速端点
   curl.exe -s -o NUL -w "%{speed_upload}" -X POST `
     --data-binary "@testfile.bin" https://speed.cloudflare.com/__up
   ```
   ⚠️ **不要用 rclone 传到 CD2 测速** —— 那是本地回环（能跑 200 MB/s），
   测的是假速度，会完全误导判断。

2. **看云端真实状态**（不是 rclone lsf）
   ```powershell
   python tools\audit_cloud.py     # 已改为查 CD2 缓存
   ```
   ⚠️ `rclone lsf` 会列出 CD2 的"幻影条目"（已接收未上传成功的文件），
   **不能作为上传成功的证据**。

3. **做控制变量测试**再下结论
   - 同样大小、只变类型 → 判断类型限制
   - 同样类型、只变大小 → 判断速度/超时问题

4. **查 CD2 队列是否堵塞**
   ```powershell
   python tools\cd2_queue_health.py --clean
   ```

## 六、这次事故中真正修好的东西（仍然有价值）

虽然根因是限速，但排查过程中确实发现并修好了几个**真实存在**的问题：

| 修复 | 说明 |
|---|---|
| **审计工具改用 CD2 缓存** | 原来用 `rclone lsf`，会被幻影条目骗。这个 bug 真实存在且危险 |
| **看门狗 LogonType S4U → Interactive** | S4U 不加载用户配置文件、无交互桌面，**CD2 这种 WinUI 应用起不来**。之前 50 次全失败就是这个原因 |
| **CD2 队列健康工具** | CD2 单线程，永久失败的任务会无限重试占死线程 → 后续全部堵死。`cd2_queue_health.py --clean` |
| **失败上传补传工具** | `retry_failed_uploads.py` |
| **BaiduPCS-Go 迁移手册** | 备用方案（含限速能力，CD2 的 WebDAV 限速无效） |

## 七、顺带确认的事实

- **CD2 应用版 vs 服务版**：本次事故与版本无关。之前认为服务版"上传线程坏了"
  （8427 次 errno -7），后来发现是我把 rclone 端口配错（19798 vs 29798）。
  **当前保持应用版**，理由：唯一真实优势（SYSTEM 账户、服务自愈）都只对
  "挂载虚拟盘"场景有意义，我们只用 WebDAV 上传。
- **Windows QoS 限速对 CD2 无效**：注册表值写入正确（注意参数要 ×8），
  但实测压不住。已删除策略。
- **CD2 自带的 `max_upload_speed_kbyps` 对 WebDAV 上传无效**：实测设 4096 后
  峰值仍 6.79 MB/s。已恢复 0。
- **rclone `--bwlimit` 只限住 rclone→CD2 这一跳**（本地回环），
  CD2 缓存后仍以全速推给百度。**限流点必须在 CD2 内部或更外层。**
