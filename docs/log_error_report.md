## 7. 结论与建议

### 7.1 必须处理（真问题）

1. **Stream-gears 异常退出（1,520 次，涉及 50 个主播）** — 最严重。
   源码 `DMR/Downloader/streamgears.py:80-83`：只有当 `not self.stoped and Onair(self.url)` 时才抛这个错，
   即 **biliup 子进程在主播仍在线时退出了**，本次录制段报废。
   追加重试逻辑（`stream_downloader.py:315-322`）会自动重连，所以不是永久丢失，但**会丢录制片段**且退避间隔递增。
   高频任务：饺子 192、呼噜 129、我真的不吃土豆 122、七个核桃 108、Lyaoay 104、行简 92。
   注意 `七个核桃` 这类会在几分钟内连续退出（14:43/14:48/14:50/14:53），是**同一场直播反复重连失败**。
   排查方向：这些主播的抖音流 CDN 不稳定 / biliup 对 FLV 断流重连处理有缺陷。
2. **磁盘写满（`[Errno 28] No space left on device`，9 条 error，2026-04-18 与 2026-05-24）** — 直接导致录制中断。
   download.log 里还有 19 条 `磁盘空间不足。(os error 112)`。需要加磁盘水位告警/自动清理。
3. **抖音 API 结构性失败（`KeyError: 'data'`，6,430 条）** — `DMR/LiveAPI/douyin.py:150` `json.loads(text)['data']`。
   抖音 `webcast/room/web/enter/` 在风控/限流/房间不存在时不返回 `data` 字段。
   它本身被 `try/except` 吞掉并降级重试（所以只记 debug），但**连锁后果是真的**：
   - `A5` 房间号解析失败 607 次（web_rid 无法转成 19 位 real_rid，任务被判定为不可用）
   - `B5` `TypeError: argument of type 'NoneType' is not iterable` 26 次 —— `GetStreamURL()` 返回 `None`，
     随后 `stream_downloader.py` 用 `.m3u8 in stream_url` 判断引擎，直接抛异常导致录制失败。**这是真正的丢录制**，建议加 None 检查。
4. **`Task ... not exists.`（56 条 error）** — `engine.py:29-31`：收到 `replay/<taskname>` 消息但该任务不在当前 task_dict 里。
   典型场景是运行中改了配置（删任务/改别名）而队列里还有旧消息。会造成该次任务静默失败。
5. **`[WinError 32] 另一个程序正在使用此文件`（4 条 error，2026-10-01~10-03）** — Cleaner 清理时文件仍被占用，
   与大文件渲染/上传并发有关。只影响清理，不丢录制。
6. **`命令执行失败: ['rclone', ...]`（1 条 error，2026-09-22 掉了颗兔牙）** — 唯一的真正上传失败。
   建议给 rclone 加 `--log-file` 并在失败时记录 stderr，否则无法定位。

### 7.2 是噪音，不用管

- **download.log 全部 1,021,056 条 WARN**。构成：
  `Non-monotonous DTS in output stream` 962,170 条、`Unexpected script tag` 45,272 条、
  `Unexpected/Different h264 sequence header tag` 6,109 + 4,311 条、`Unexpected aac sequence header tag` 3,047 条。
  这是 biliup FLV 解析器对抖音流的常规抖动输出，**零 ERROR**，流媒体内容正常。
  只有 69 条 `deadline has elapsed` 和 19 条 `磁盘空间不足` 值得留意。
- **弹幕链路 C1–C7 共 814 条 error**：`获取弹幕超时，正在重试...` 375、`弹幕下载线程异常退出，正在重试...` 225、
  `Websocket Closed` 113、`KeyError: 'nickName'` 64、`Cannot write to closing transport` 34、`KeyError: 'data'` 3。
  看源码 `danmaku.py:194-212`：全部走"取消 task → sleep → 重建 task"的自动重连，**会自愈**。
  后果只是弹幕文件出现几秒到几十秒的空白，视频本身不受影响。
  `KeyError: 'nickName'`（`danmaku/douyin/__init__.py:138/153 decode_msg`）是抖音弹幕消息里缺字段，
  属于消息格式变化，只丢单条弹幕。
- **`无法获取视频大小，使用默认值 [1920, 1080].`（152 条 warning）** — `stream_downloader.py:207-210`，
  ffprobe 探测直播流失败时回退默认分辨率。**会自愈**，但若原流不是 1920x1080，弹幕排版会偏。
- **抖音 GetRoomInfo / GetStreamerInfo 的 debug 级 KeyError** —— 有 `retry_safe` 兜底，绝大多数下一次就成功。
- **`输出文件名 ... 不合法或已存在，已更改为 ...(1).mp4`（4 条 warning）** — 正常改名，无影响。
- **`不存在视频文件 ...，跳过渲染`、`分段失败`、`cannot schedule new futures after shutdown`** — 共 10 条，
  都是短暂的竞态（文件被删/进程关闭），量级可忽略。

### 7.3 一次性环境事故（不是程序 bug）

- **2026-08-18 ~ 08-19 DNS 解析故障**：42,718 条 `NameResolutionError: Failed to resolve 'live.douyin.com'`，
  集中在两个文件 `DMR-20260810.log.2026-08-17`(13,227) 和 `.2026-08-18`(29,491)，
  速率稳定在约 1,600 条/小时（≈27 条/分钟）——说明**重试循环在 DNS 挂掉时没有任何退避**，把日志刷到 20 MB/天。
  建议：给 `LiveAPI` 的连接重试加退避 + 熔断，否则下次 DNS 故障还会刷爆磁盘。
- **2026-07-09 18:24 短暂断网**：62 条 DNS 失败 + 31 条 `获取抖音ttwid失败` + 32 条 `Message:... raise an error`，
  所有任务在同一秒集中报错，是该时段网络中断所致。

### 7.4 统计口径提醒

- 本工具把大量"错误"写成 `debug` 级（`LiveAPI\__init__.py:60/66/78` 等处的 `logger.debug(f'... Error: {e}')`）。
  **只看 error 级统计会漏掉 6,430 条抖音 API 失败**，建议把这些改成 `warning` 或加专门计数器。
- `Stream-gears 异常退出` 在日志里会重复 3 次（`stream_downloader` error + `engine` debug JSON + `liveevents` info），
  按记录数统计会虚高 3 倍；本报告已按**去重事件数 1,520** 计。
- 追加在 `Stream-gears 异常退出` 后面的是 `log[-1000:]`（biliup 最后 1000 字符），
  **约 57% 的情况（865 / 1,520）只是 FLV 噪音、没有任何有效诊断信息**；
  其中 38 次含 Python Traceback，但被 1000 字符窗口截断，异常类型不可读。
  建议把完整子进程日志落盘，否则这类问题永远无法定位。
