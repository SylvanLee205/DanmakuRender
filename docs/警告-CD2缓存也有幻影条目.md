# ⚠️ 重要警告：CD2 缓存也不能完全相信

**记录日期**：2026-10-06
**发现者**：用户（在百度网盘网页上看到实际文件数与缓存不符）

---

## 结论先行

**验证文件是否真的在云端，唯一 100% 可信的方法是：在百度网盘网页/客户端上看。**

| 验证方式 | 可信度 | 说明 |
|---|---|---|
| **百度网盘网页/客户端** | ✅ **100%** | 唯一真值 |
| CD2 **服务版** 缓存（`dir_cache.sqlite`） | 🟠 与 rclone 一致，未发现幻影 | 可用，但仍建议抽查网页 |
| `rclone lsf` / `lsjson` | 🟠 与服务版缓存一致，但**协议层会列已接收未上传的文件** | 不能单独作证据 |
| CD2 **应用版** 缓存 | 🔴 **发现含幻影条目** | **不要用于验证** |

---

## 事故经过

2026-10-06 晚上排查上传问题时，我"验证"过 4 个文件确实在云端：

```
苏苏没烦恼-2026年09月30日20点46分（弹幕版）.mp4   1,453,650,637 字节  "✅ 字节一致"
苏苏没烦恼-2026年09月30日21点46分（弹幕版）.mp4   1,473,817,238 字节  "✅ 字节一致"
苏苏没烦恼-2026年09月30日22点46分（弹幕版）.mp4     606,184,169 字节  "✅ 字节一致"
苏苏没烦恼-2026年10月04日00点24分（弹幕版）.mp4      17,003,459 字节  "✅ 字节一致"
```

验证方法是读 **CD2 应用版**的 `dir_cache.sqlite` 的 `files` 表，
发现条目存在且大小完全一致。

**但用户打开百度网盘网页一看：这 4 个文件根本不在。**

## 为什么会这样

CD2 的 `files` 表记录的是**它认为云端有什么**。当 CD2 接收了一个 WebDAV 上传
请求（`create_file`），它会：
1. 立即在本地缓存里记下这个文件条目（所以 WebDAV 列目录能看到）
2. 异步把数据传给百度
3. **如果第 2 步失败，缓存条目不会回滚**

结果就是：**本地缓存里有、大小也对、但百度那边没有。**

这就是"幻影条目"（phantom entry）。应用版的缓存里这种现象更明显。

## 对排查的影响（血的教训）

我基于这个错误的"验证结果"，得出了好几个错误结论：

| 错误结论 | 实际 |
|---|---|
| "补传成功，字节一致" | 根本没到云端 |
| "审计显示丢失 0 个" | 审计读的是应用版缓存，不可信 |
| "CD2 恢复正常了" | 只是缓存看起来正常 |

## 正确的做法

### 1. 日常审计

用 `tools\audit_cloud.py`。它会：
- **自动判断当前用哪个 CD2 实例**（从 rclone.conf 的端口推断）
- 读那个实例的 `dir_cache.sqlite`
- 缓存是冷的会先 `rclone lsf -R` 预热

但它**仍然是缓存口径**。所以：

### 2. 关键节点必须抽查网页

补齐重要文件后、或每次大动作之后，**去百度网盘网页看一眼**那几个目录。

### 3. 交叉验证的判据

真正确认一个文件在云端，至少要满足：
- ✅ rclone 能列出它（**且**）
- ✅ 当前 CD2 实例的缓存有它、大小一致（**且**）
- 🏆 **抽查看百度网盘网页**（最终真值）

只有前两条时，仍要留一个怀疑：可能是幻影。
