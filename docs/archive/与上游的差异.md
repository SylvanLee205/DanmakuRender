## 一、为什么写这份文档

改到第 50 个提交时发现：**说不清自己和上游到底差在哪了**。
新人（或三个月后的自己）打开仓库，看到 `DMR/` 目录结构和上游一样，
很容易以为"这是个普通 fork"，然后按上游的方式去改，踩一遍我们踩过的坑。

所以把差异按"保留 / 新增 / 替换 / 移除"四类列清楚。
判断标准只有一条：**这个模块是上游的还是我们的**。

## 二、完整保留（上游的，没动）

这些是原版的设计，实测好用，**不要动**：

| 模块 | 说明 |
|---|---|
| `DMR/engine.py` | 引擎 + PipeMessage 消息路由 |
| `DMR/Config/` | 配置合并机制（`default.yml` → `global.yml` → 任务 yml 三层） |
| `DMR/Downloader/` 的下载器抽象 | ffmpeg / streamlink / streamgears 三引擎的分发 |
| `DMR/LiveAPI/` | 各平台 API 适配层 |
| `DMR/Render/dmrender.py` 的渲染调度 | 任务队列、超时、硬件/软件编码降级 |
| `main.py` 的启动流程 | 参数解析、日志初始化、插件加载 |

**特别注意 `Config/` 的合并机制**：任务配置里没写的键会从 `global.yml`
继承，这让我们能把 33 个任务配置压到 22 行（只有 url 和 output_dir）。
改任何配置项前先读 [`project_state.md` 的 3.2 节](project_state.md)。

## 三、新增（原版完全没有）

### 3.1 状态持久化与启动对账 —— `DMR/state/`

原版重启后"哪些分段录完了、传没传、清理没有"全丢，只能人工翻。

- **`logs/dmr_state.db`**（SQLite）：录制场次、每个分段的产物、上传组归属
- **启动对账**（reconciler）：重启时比对各状态库与磁盘，把"已录完但没传"的
  分段重新送回处理链
- **孤儿分段自动接管**：进程被杀留下的 `[正在录制]xxx-Part000.ts`，
  对账时按 `output_name` 模板改名并补派渲染
  （`liveevents.py::_promote_intermediate_name`）
- **一致性保护**：状态库里的任务若不在当前配置中，默认隔离放行并告警；
  配置为空时仍拒绝启动（那才是 config_path 指错的真信号）

### 3.2 延迟清理 —— `DMR/Cleaner/`

原版基本没有清理逻辑。现在：

```yaml
clean_args_task_default:
  dm_video:
    method: delete
    delay: 86400        # 24 小时后悔期
    w_srcfile: True     # 连带删源视频 + 源弹幕
    w_dmfile: False     # 弹幕版本身永不删
```

- 待删清单落盘到 `logs/pending_clean.json`，**重启不丢**
- 失效条目（文件已不在）自动剔除，幂等
- **修过的坑**：命中"跳过上传"规则的分段永远不进清理流程，
  实盘积压 42.9 GB。现在 `_check_for_upload` 末尾会补一次清理判定

### 3.3 字形安全清洗 —— `DMR/Downloader/Danmaku/glyphs.py`

弹幕里某些字符会让**整场渲染失败**，而且硬件/软件编码都救不了
（根因在 libass 字幕帧，不在编码器）。详见
[排查记录-20261102](排查记录-20261102-渲染崩溃三个真凶.md)。

三类真凶：无字形字符（注音ㄓ U+3103）、彩色 emoji 字体
（国旗指示符 U+1F1E8 回退到 SegoeUIEmoji）、源视频损坏帧致 libass
输出帧 stride 算错。

判据是 `color - primary`（主字体没有、彩色字体才有），
**不是** `color`（会连 ASCII 一起删）也不是 `color - plain`（会漏）。

### 3.4 无人值守运维体系 —— `tools/` + 桌面 bat

原版要人盯着。现在：

- **开机自启三层**：Startup .cmd（登录自启，交互式有窗口）→
  SessionWatch（登录+解锁触发，跨会话迁移）→ Boot 任务（session 0 常驻兜底）
- **优雅停止**：`stop_dmr.py` 创建 `.temp/graceful_stop_<PID>`，
  `main.py` 轮询到就走 `dmr.stop()` → ffmpeg 收到 `q` 写完当前段并改名
- **进程发现改用 psutil**：原来调 `powershell.exe` 列进程，
  无人值守/沙箱环境里它不在 PATH 上，脚本在干活前就崩
- **一键加主播**：`add_room.py` 读剪贴板 → 自动取名 → 写配置 → 热加载
- 另有 `rename_orphans.py` / `clean_skipped_backlog.py` /
  `purge_task_state.py` / `sync_full_backup.py` / `dmr-status.ps1` /
  `post_boot_check.py`

### 3.5 测试 —— `unit_tests/`

503 个 unittest，覆盖状态库、清理链路、自启判断、下载任务重试、
字形清洗、配置合并。原版没有测试。

## 四、替换（原版有，我们换掉了）

### 4.1 上传：B站 → rclone 网盘

- 原版用 `biliup` 投 B站；现在用 **rclone**（经 CloudDrive2 挂载）传百度网盘
- `requirements.txt` 去掉 biliup，加 rclone/psutil/fonttools 等
- **跳过上传规则**：横屏 + 码率≥2500kbps 或帧率≥40fps 直接跳过
  （省 Arc 显卡占用，那卡蓝屏过）
- 上传前校验：mp4 读不出时长**拒绝上传**（防半成品）

### 4.2 下载参数调优

`configs/global.yml`（git 忽略）里的实盘调优值，与 `default.yml` 不同：

| 参数 | 默认 | 现在 | 为什么 |
|---|---|---|---|
| `-rw_timeout` | 10s | 15s | 20s 时停滞 18.8 秒刚好卡在门下，ffmpeg 从不认为出错 |
| `disable_lowspeed_interrupt` | false | false（改回） | true 会把"重启纠正"变成"沉默留洞" |
| 抖音接口超时 | 5s | 10s | 配合 newtask 自动重试 |

## 六、为什么不再跟上游合并

三条，按重要性排：

1. **上游停更**。最后一次提交 2026-10-10（"feat: 录制状态持久化与可靠恢复"），
   我们 10-15 就合并过来了（见
   [`docs/上游合并与部署记录-20261015.md`](上游合并与部署记录-20261015.md)），
   之后至今无新提交。
2. **改动面已经错开**。我们改的（状态库、清理、rclone、自启）正是上游没做的；
   上游如果更新，大概率是加平台/改 API，和我们这条线不冲突但也不互补。
3. **无 LICENSE**。上游仓库没有 LICENSE 文件，没有 Copyleft 义务，
   可以自由改名/重构（道义上保留致谢，README 里已致谢）。

**如果哪天上游出了非合不可的安全修复**：因为 `prod-sync` 是基于 v5 建的，
仍可以用 `git cherry-pick` 或 `git merge origin/upstream` 单点合并，
不影响我们这条线。真正断掉合并能力的是"改包名/重构目录"，所以那件事
一直没做。

## 七、给后续维护者的话

- **改 `DMR/` 下的代码必须重启才生效**（配置热加载不覆盖代码）。
  这个坑踩过三次。
- **改 `configs/global.yml` 同样必须重启**，DMR 只会打警告不自动应用。
- **停用主播是两步**：配置挪进 `configs/temp/` + 跑
  `tools/purge_task_state.py --apply`。只做第一步会让 DMR 拒绝启动。
- **任务名 ≠ 录像目录名**（`output_dir` 可以指向任何目录）。
  这个坑出现过三次：迪佳奥特曼→我已经不会再流泪、jun'jun→君君、
  断尾人类→直播回放/断尾人类。
- 看 [TODO.md](TODO.md) 的"未完成"和
  [maintainer-log.md](maintainer-log.md) 的"已完成的为什么"，
  比读代码快。
