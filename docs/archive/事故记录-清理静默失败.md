# 事故记录：清理静默失败 6 小时（2026-10-07）

## 一、现象

**终端持续报错**（用户报告"终端刚才一直提示 name xxx is not defined"）：

```
File "F:\DanmakuRender_AutoUp\DMR\Cleaner\__init__.py", line 93, in _clean_subprocess
清理错误 name 'basename' is not defined
```

**影响**：从 **16:52 到 22:16**，所有清理任务**全部失败**。
TG家里蹲、荞麦拌面、vvu 等 7 个源视频（约 2.3 GB）滞留在磁盘上没被删除。

## 二、根因（我的错）

我在改清理日志格式时，把 `Cleaner/__init__.py` 里的消息改成用 `basename()`：

```python
_base = basename(file.path)          # ← 用了 basename
...
self.logger.log(25, f'正在清理原文件: {_base}（含弹幕文件）')
```

**但忘了在 import 里加 `basename`**：

```python
from os.path import exists, isdir, isfile, abspath, dirname
#                                                    ↑ 没有 basename
```

**更隐蔽的是**：文件里有 `from DMR.utils import *`，看起来像能兜住，
但 `DMR.utils` **并没有导出 basename**（它只在个别子模块内部用）。

**为什么 `py_compile` 查不出来**：语法完全正确，只有真正执行到那一行才抛 `NameError`。
而清理是个**异步子进程任务**，异常被 catch 住只打了日志 —— 所以表现成"静默失败"。

## 三、修复

```python
from os.path import exists, isdir, isfile, abspath, dirname, basename
```

顺便全面检查了我这些天改过的其他文件，`basename` 都有正确导入：
| 文件 | 用 basename | 导入 |
|---|---|---|
| `Cleaner/__init__.py` | 2 次 | ❌ 缺失 → **已修** |
| `Render/__init__.py` | 2 次 | ✅ |
| `Uploader/__init__.py` | 4 次 | ✅ |
| `stream_downloader.py` | 1 次 | ✅ |

## 四、新增自检工具 `tools/check_imports.py`

这个 bug 本来可以提前发现，所以做了**三层检查**：

```
第一层：静态检查（AST 找"用到的名字没导入"）
        有 import * 的文件会跳过（判不了）
第二层：运行时检查（import 每个模块，确认关键名字真的可用）
        ← 这一层能抓到 Cleaner 的 basename 问题
第三层：真实清理测试（造临时文件走一遍 delete，确认文件真被删）
        ← 这一层本来能提前抓到
```

用法：
```powershell
python tools\check_imports.py
```
当前结果：**三层全通过**。

## 五、⚠️ 排查中我犯的第二个错（差点造成损失）

为了清理滞留文件，我临时写了个一次性脚本，它有**两个致命缺陷**：

```python
# 我写的危险代码
if f.endswith('.mkv') and not os.path.exists(dm):
    continue          # ← 只对 .mkv 做了安全检查
# .ass 文件没有检查，直接删  😱
```

结果删掉了 2 个 `[正在录制]` 的 .ass（0 字节，DMR 继续写入，**无实际损失**）。

本来有"正在录制不清理"的保护，是我绕过它才出的事。

## 六、新增安全清理工具 `tools/clean_sources.py`

把所有防护固化下来，以后清理一律用它：

| 防护 | 对应教训 |
|---|---|
| 跳过 `[正在录制]` / `[正在渲染]` / `[正在上传]` 前缀 | 2026-10-07 我删了正在录制的文件 |
| 跳过 `.part` / `.tmp` / `.converting` | 中间文件不能删 |
| 只处理超过 N 分钟（默认 30）没被修改的文件 | 防正在写入 |
| 必须"内容已在别处"才能删，二选一：<br>a) 本地有 `（弹幕版）.mp4`<br>b) **云端已有该分段** | 防删掉还没渲染的 |
| 默认 **dry-run**，加 `--apply` 才真删 | 防手滑 |
| 删除前打印完整清单 | 可复核 |

**`--min-age` 的作用**：源文件刚录完时可能还在被处理，等 30 分钟再清更安全。

**为什么加云端校验**：本地渲染产物可能已被正常清理掉，这时源文件其实
可以安全删除（内容已在云端）。只按本地产物判断会过于保守 ——
实测有 12 个文件（1.11 GB）因此永久滞留。

### 用法

```powershell
# 先看会删什么（不实际删除）
python tools\clean_sources.py --show-skipped

# 确认后执行
python tools\clean_sources.py --apply

# 只清 2 小时以上的（更保守）
python tools\clean_sources.py --apply --min-age 120
```

### 实测效果

```
可安全清理 16 个文件，共 1.76 GB：
   654.1 MB  [云端已有]   小鱼大王\小鱼大王-2026年10月01日01点19分.mkv
   515.6 MB  [本地已渲染] vvu\vvu-2026年10月02日20点36分.mkv
   ...
被保护跳过的 3 个：
   [跳过] [正在录制]哭哭不嘻嘻-...ass  <- 文件名含"正在录制"标记
   [跳过] [正在录制]...flv.part        <- 同上
   [跳过] [正在录制]...flv.part        <- 同上
```

执行后释放 1.76 GB，正在录制的文件完好无损。

## 七、排查过程中的两次误判（记录以免重复）

我两次看到 `.part` 文件"从 765 MB 变成 0"，都以为录制中断了：

| 时刻 | 我以为 | 实际 |
|---|---|---|
| 23:22 | 705.8 MB 的 .part 消失了 | 文件仍存在，是**读文件名的瞬间被轮转**导致的误读 |
| 23:24 | 765.3 MB 的 .part 消失了 | 同上 |

**验证录制正常的正确方法**：
1. 看 `[正在录制]` 前缀的文件是否还在（在 = 录制中）
2. 看 `.ass` 是否有写入活动（大小或 mtime 变化）
3. 看 `streamgears_wrapper` 进程是否存活

**不要只看单次文件大小快照** —— 文件名轮转会产生误导。
