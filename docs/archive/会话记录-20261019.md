## 1. 录制引擎全局切换：streamgears → ffmpeg + ts

### 为什么换（全是实测证据）

| 问题 | streamgears + FLV | ffmpeg + TS |
|---|---|---|
| 坏流 | Rust **panic**，历史累计 **1751 次**，单日最高 42 次 | 跳过坏帧继续 |
| 停滞检测 | ❌ 完全没有 | ✅ "15 秒无输出就重试" |
| 录制可见性 | ❌ 内存缓冲：`.flv.part` 冻结 **495.9 MB 达 74 分钟**，结束时变 1351.6 MB（855 MB 一直在内存） | ✅ 流式写入，体积实时增长 |
| 容器真实性 | ❌ `output_format: mkv` 是**假的** —— ffprobe 实测 `format_name=flv` | ✅ 真 `mpegts` |
| 时长诚实度 | ❌ 38 分钟报成 **217 分钟**（5.7 倍） | ✅ 截断后仍准确 |
| 断流恢复 | 退出 + 外层重试 | ✅ 配置已有 `-reconnect 1 -reconnect_streamed 1` |

### 实测数据（ts vs flv 截断对比）

把文件截断到 50%，看还能不能用：

| 容器 | ffprobe 报的时长 | 实际数据 | 解码错误行 |
|---|---|---|---|
| **ts** | **10.07 秒（准确）** | 10 秒 | **2 条** |
| flv | 20.02 秒（虚报） | 10 秒 | **46 条** |
| mkv | 20.02 秒（虚报） | 10 秒 | 1 条 |

**结论：TS 天生抗截断，中断恢复从"修复"降级成"改名"。**

### 全链路验证（用真实抖音直播间 765184155745）

```
01:11:11  开始录制  → [正在录制]_引擎测试-...-Part000.ts
01:13:10  分段完成（正好 120 秒）→ 改名 .ts  23.53 MB
01:13:12  开始渲染
01:13:25  渲染完成（13 秒）→ （弹幕版）.mp4   5.86 MB
源 .ts: 23.53 MB / mpegts / 120.985 秒
产物 :  5.86 MB / mp4 / 121.050 秒   → 比例 100.05%
```

### 实测反驳的两个"必备参数"

**① `-bsf:v h264_mp4toannexb` 不需要**

掐掉 TS 文件开头 45%（去掉头部 SPS/PPS），看剩下的能不能解码：

```
no-bsf    6624 KB    掐头后能解码 ✅
with-bsf  6624 KB    掐头后能解码 ✅
         ↑ 字节数完全一致
```

ffmpeg 存 TS 时**自动**做 AVCC→AnnexB。而且写死 `h264_` 会**搞坏 HEVC 源**（抖音很多 HEVC）。

**② `-avoid_negative_ts make_zero` 对 mpegts 几乎无感**

```
默认        首帧 pts=2.403089
make_zero   首帧 pts=2.403089   ← 完全一样
```

真正解决"断流后源时间戳归零"的是：**分段 + 每段独立 ffmpeg 进程 + `-reset_timestamps 1`**（本来就有）。

### 新增 `tools/recover_ffmpeg_segments.py`

ffmpeg 不产生 `.part`，崩溃会留下 `[正在录制]*-PartNNN.<ext>`。
因为 TS 抗截断，**不需要修复**，只需改名 + 按 14 位时间戳配对 `.ass`。
已接入 `main.py` 的 `_startup_recover`（在 `recover_part` 之前跑）。

## 2. 🔴 字幕滤镜会毁掉坏时间戳文件的时间轴

### 现象

`哭哭不嘻嘻-2026年10月19日03点39分.ts`（1574 MB / 3602 秒）怎么都渲染不出弹幕版：

- QSV：`-22 Invalid argument`，0.44 秒秒退，`frame=0`
- libx265：跑到 7 分钟时 `0xC0000005` 访问冲突崩溃
- 产生的 59.3 MB「产物」是残file：**`moov atom not found`**，本地和网盘都播不了

### 只改一个变量的对照实验

同一文件、同一 ffmpeg（`n9.0.2-22`）：

| 组合 | 结果 |
|---|---|
| 全文件 **不带** subtitles 滤镜 | ✅ **3609s / 源 3602s，180 秒完成，316 MB** |
| 全文件 **带** subtitles 滤镜 | ❌ QSV 秒退 / x265 崩 |
| 单块 600s 带字幕 | ⚠️ 能跑，但输出 **1002s**（应 600s，多 67%） |

**根因**：源文件 600–1800 秒这段时间戳坏了（帧密度是正常的 1.67 倍）。
libass 要按时间轴组织帧，**坏时间戳经过滤镜图会把输出时间轴整体拉长**，再叠编码器就崩。

> 用户自己的 `UniversalEncoder_v85.py` 能编码成功（3513s，时长正确）—— 因为它**不烙字幕**。
> 所以「能编码」和「能烙字幕」是两件不同的事。

### 解法：两步渲染（`tools/two_step_render.py`）

```
第一步  TS → 干净 MP4（不烙字幕）   667.3 MB  3609s/源 3602s  182 秒   ← 修时间轴
第二步  干净 MP4 → 烙字幕            402.1 MB  3609s/源 3602s  185 秒
最终    402.1 MB  hevc 1088x1920  视频 3609.4s / 音频 3609.3s（音画同步）✅
```

用同样方法救回了 `Part001`：375.1 MB / 3513s / 音画同步。

### 判断信号

```bash
# 成功 → 源可编码，问题在字幕滤镜 → 用两步渲染
ffmpeg -err_detect ignore_err -i src.ts -c:v hevc_qsv -global_quality:v 22 out.mp4

# 也失败 → 源本身坏了，两步渲染也救不回来
ffmpeg -err_detect ignore_err -i src.ts -c:v hevc_qsv out.mp4
```

## 3. 🔴 moov 缺失的残file被当正常产物上传

### 漏洞

原来的时长校验：

```python
if src_dur > 0 and out_dur > 0:      # ← out_dur 为 0 时整段校验静默跳过
```

而 **moov 缺失的文件，ffprobe 正好读不出时长**（返回 -1）→ 校验被跳过 → 残file当正常产物上传。

### 修法

```python
if out_dur <= 0:
    # 读不出时长 = 一定是坏文件（moov 未写入 / 未收尾）
    return False, '渲染产物不可读（moov 缺失 / 文件未收尾）'
```

实测：截断一半的 mp4 → `get_duration = -1` → 现在会被判失败。

**影响面**：扫了近 2 天 46 个产物，只有那 1 个坏的，其余 45 个正常。

## 4. 🔴 延迟清理定时器重启即丢（6.42 GB 泄漏）

### 问题

`Cleaner` 用 `threading.Timer` 挂 48 小时延迟，而状态在派发瞬间就写成 `cleaned`（终态）。
进程一重启定时器蒸发，`CLEANED` 是终态没人再管 → 源视频永久残留。

**实测**：10-19 00:06 一次重启就让 **38 个源视频 / 6.42 GB** 的删除定时器全部蒸发。

### 修法

新增 `logs/pending_clean.json` 作为**权威待删清单**：

- `add_task(delay>0, method=delete)` 时落盘
- 真正删完后移除；失败保留待重试
- `Cleaner` 启动时重读：已到期的立即补删，未到期的重新 arm
- 文件已消失的条目自动剔除（幂等）
- 删除改幂等（并发重复删除报 PermissionError 时，只要文件确已不存在就算成功）

**踩的坑**：第一版 `add_task` 已持有 `self._lock`，而 `_journal_add` 又取同一把锁 →
**普通 Lock 不可重入 → 直接死锁**。改成 `RLock`。

**实测**（`tools/test_pending_clean.py`）：4/4 通过
（已过期的补删 / 重启后到期的删掉 / 未到期的保留 / 清单正确留下）

## 5. 🔴 渲染失败时状态不收敛

`onTaskError` 的 docstring 写着"修复活体泄漏"，但**事件表里从未接线**：

```python
'render/error':   self.defaultEvent,   ← 应为 onTaskError
'uploader/error': self.defaultEvent,   ← 应为 onTaskError
```

**后果**：失败时 `wait` 里的 `request_id` 永远清不掉 → 清理逻辑的"wait 非空不清理"防线永远挡着 →
源视频永不清理；且分组永远达不到终态，只能等 72 小时超时释放。

**修法**：三个 `error` 事件接 `onTaskError`；`ArtifactState` 新增 `FAILED` 纳入终态；
补 `failed` 状态映射（之前写了也不会持久化）。

> 这是**第三次**踩「方法定义了但没人调用」这个坑（前两次：GOP、跳过上传规则）。

## 6. 🔴 崩溃循环：孤儿任务拒绝启动

### 事故

我用临时测试任务 `_引擎测试` 验证 ffmpeg 引擎，删掉配置后，状态库里残留的记录让
`_check_task_set_consistency` 拒绝启动 → **12 秒一次的崩溃循环**，
只能删整个 `dmr_state.db` —— 会连带丢掉所有正常任务的历史。

### 修法

孤儿任务分两类：

- 产物**全是终态**（或根本没有产物）→ 自动 `purge_task` 并继续启动
- 还有**非终态**产物 → 仍然拒绝（这才是真正可能误删有价值历史的场景）

新增 `StateRepository.purge_task()`，显式删 artifacts + sessions + upload_groups
（不依赖外键级联 —— `delete_session` 的 docstring 说级联，实际只删 sessions 行）。

## 7. 🟠 孤儿 ffmpeg 双录

引擎切 ffmpeg 后，**重启 DMR 不会杀掉旧的 ffmpeg 下载子进程**。
它们变孤儿继续录，新实例又开一场 → 同一主播两份文件、双倍占盘。

**实测**：哭哭不嘻嘻 同时有 **3 个 ffmpeg**，其中 2 个是孤儿，两个文件以 5.2 MB/20s 同步增长。

**修法**：`cleanup_duplicate_streamgears.py` 新增 `FF_Q`，杀所有 `-segment_time` 的 ffmpeg。

> **判据必须是 ASCII**：最初写的是 `'*直播回放*'`，而中文经 `Python → powershell -Command`
> 传递会被 ANSI 代码页搞坏，查询永远返回空 → 杀孤儿那步形同虚设。

## 8. 🟡 其他修复

| 问题 | 修法 |
|---|---|
| `_check_for_clean` 只认 `uploaded`，导致跳过上传的文件永不清理 | 接受 `upload_skipped`（**`failed` 仍排除** —— 渲染失败时源是唯一副本） |
| `resume_recovered` 只续上传、不续渲染 | 新增 `_dispatch_pending_renders`，加两道前置检查（不渲染正在录制的、必须有弹幕） |
| 状态库用 `segment_id`、代码用 `idx+1`，丢消息后段号错位 | 新增 `_seg_no()`，优先 `segment_id`，8 处全改 |
| `ffmpeg.py` 时长解析 `m` 用了 `[0]` | 实测 `time=01:23:45` 被算成 3705s 而非 5025s（差 22 分钟），直接进 `dmw.time_fix()` → **弹幕时间轴错位** |
| `_check_for_clean` 参数被循环变量遮蔽 | 传入的 `group_id` 完全不生效 |
| 渲染进程 `wait()` 无超时 | 加 `wait(timeout=源时长*10+600)`，超时 kill |
| `_free_state_memory` 用单一 `final_status` | 改"可接受状态集"，`w_dmfile=False` 时接受 `uploaded` |
| 分辨率探测的 glob 方括号 | `[正在录制]` 被当字符类，**从未成功过**；改 `glob.escape()` |
| 配置快照误收 `.bak-*` | 删掉过期备份后启动报「丢失 1 个配置」；改为跳过 `.bak/~/tmp` |
| 待删清单清空不落盘 | 只在有到期项时才写回，导致清单永远清不空 |
