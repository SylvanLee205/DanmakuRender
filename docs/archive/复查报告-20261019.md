## 1. 🔴 P0-1 延迟清理用进程内 Timer，重启即永久丢失（磁盘只增不减）

### 位置
- `DMR/Cleaner/__init__.py:71-72`
- `DMR/Task/liveevents.py:873-879`、`:906-909`

### 机理
```python
# Cleaner.add_task: delay>0 时用进程内定时器
if config.get('delay', 0) > 0:
    threading.Timer(config.get('delay'), self.clean_executors.submit, ...).start()
```
`configs/global.yml` 的 `clean_args_task_default` 是 `delay: 172800`（48 小时后悔期）。

问题在于**状态在派发清理的瞬间就写成了 `cleaned`**：
```python
# liveevents._check_for_clean
self.state_dict[group_id][idx]['src_video']['status'] = 'cleaned'
self._sync_artifact(group_id, 'src_video', idx + 1, state=ArtifactState.CLEANED)
```
而真正的 `os.remove` 要等 48 小时后由 Timer 执行。Timer 是守护线程，**进程一退出就消失**，
且 `CLEANED` 是终态 —— 重启后 `reconcile` 与 `resume` 都不会再处理它。D4 回收还会在产物全部终态后
删掉整条场次记录，连"这个文件本该被删"这件事都一起消失。

### 实测证据
1. 进程启动次数（日志里 `DMR engine started`）：10-15 当天 **10 次**，10-16～10-19 每天 3～4 次。
   本次是 10-19 **00:06** 启动。
2. 磁盘上 38 个源视频 `mkv` 共 **6.42 GB**（全部是 10-18 产生），其清理派发时间都在 10-18 14:00–23:30，
   48 小时到期时间在 10-20 之后 —— 但 00:06 的重启已经把**所有**定时器清空。
3. 铁证（状态库 vs 磁盘）：

```
DB 记 cleaned 的产物 52 个，其中文件仍在磁盘上 1 个：
  src_video    1351.6 MB  ./直播回放/断尾人类\断尾的人类不会喵-2026年10月18日20点56分.mkv
```
   即"库里说删了，文件还在，而且不会再有第二次机会"。

### 影响
用户核心诉求"渲染完只删源视频、弹幕版永久保留"在当前实现下**部分失效**：源视频会持续堆积，
最终表现与 2026-10 月初那次「165 GB 累积」完全一样，只是速度变成每次重启泄漏一批。

### 建议修法（两选一）
- **A. 最小改动**：把待删清单落盘（`logs/pending_clean.json` 或状态库新表），记录
  `{path, due_ts, taskname, request_id}`；`Cleaner` 启动时重新 arm 所有未到期的项，到期或已过期则立即删。
- **B. 语义修正**：`CLEANED` 只在 Cleaner 真正执行后写入。需要把 `cleaner/end` 接到
  `onCleanEnd`（现在是 `defaultEvent`），并把 delay 语义改为"到期时间"而不是"从现在起的秒数"。

> A 的改动面小、不影响状态机；B 更正确但要动清理链路。**改清理链路前必须跑 `tools/test_clean_order.py`。**

## 2. 🔴 P0-2 渲染/上传失败时状态不收敛 —— `onTaskError` 从未被注册

### 位置
- `DMR/Task/liveevents.py:69-74`（事件表）
- `DMR/Task/liveevents.py:1019`（`onTaskError` 定义）

### 实测
```
render/end       -> onRenderEnd
render/error     -> defaultEvent     ← 应为 onTaskError
uploader/end     -> onUploadEnd
uploader/error   -> defaultEvent     ← 应为 onTaskError
cleaner/end      -> defaultEvent
cleaner/error    -> defaultEvent
onTaskError 是否被任何键引用: False
```
`onTaskError` 的 docstring 明确写着"修复活体泄漏"，但**接线漏了**，所以那段修复从未生效。
它属于本项目总结的"B 类 bug：方法定义了但没人调用"，而 `feature_audit.py` 的 D 段接线检查**没有抓到**
（它只检查方法名是否在别处出现，`onTaskError` 出现在自己的 docstring 里，被误判为有调用）。

### 现场证据（10-18 真实渲染失败）
```
[engine][debug]: {'source': 'render', 'target': 'replay/断尾人类', 'event': 'error', ...}
[liveevents][PROGRESS]: 断尾人类: 渲染视频...（弹幕版）.mp4时出现错误: ...
```
这些消息全部落到 `defaultEvent`：只打一行日志，**`wait` 里的 request_id 不清除、状态不置 failed**。

### 影响
- 失败分段的 `dm_video` 永久停在 `rendering`，`wait` 非空 → 清理逻辑第 2/3 道防线永远挡住源视频清理；
- 分组永远达不到终态，只能等 72 小时超时释放（`state_dict` 内存滞留）；
- 上传失败同理：`uploading` 永不收敛，重试入口也失去依据。

### 建议修法
```python
'render/error': self.onTaskError,
'uploader/error': self.onTaskError,
```
并把 `cleaner/error` 一并接上（或按 B7.4 决定删除）。改完后注意 `_free_state_memory` 的
`final_status` 不含 `'failed'`，失败分组仍要等 72h —— 建议顺带把 `failed` 视为终态。

## 3. 🟠 P1-1 `upload_skipped` 不被清理流程认作可清理

### 位置
`DMR/Task/liveevents.py:849`
```python
if info['status'] != 'uploaded':
    continue
```

### 冲突点
`README-魔改版.md` 第 8 节明确写过：

> **状态机要点**：跳过时状态标成 `upload_skipped`。而 `_check_for_clean` 必须把 `upload_skipped`
> **也认作可清理状态**，否则命中跳过规则的文件会永远清理不掉、原视频一直堆积（这个 bug 实测踩到过）。

但当前代码只认 `uploaded`。日志里能看到跳过规则**确实在命中**（横屏高帧率/高码率）：
```
小鱼大王: dm_video 命中跳过上传规则（命中 2/1 项 [横屏1920x1080, 帧率60fps>=40]）  ×8
灰蒙蒙/掉了颗兔牙/蓝羊羊不懒: src_video 命中跳过上传规则（码率3263kbps>=2500）  ×多处
```
`dm_video` 一旦被标 `upload_skipped`，就再没有事件把它推进到 `uploaded`，
`_check_for_clean` 永远不会为它触发 → **对应的源视频永不删除**（横屏高码率恰恰是最占空间的）。

### 建议修法
```python
if info['status'] not in ('uploaded', 'upload_skipped'):
    continue
```
并保留 `keep_self`（`w_dmfile: False`）逻辑：跳过上传的 `dm_video` 只触发 `w_srcfile` 清理，
弹幕版本地保留。**改完必须跑 `tools/test_skip_upload_flow.py` 与 `tools/test_clean_order.py`。**

## 4. 🟠 P1-2 恢复重驱动只能"续上传"，不能"续渲染"

### 位置
- `DMR/Task/liveevents.py:249-326`（`resume_recovered`）
- 关键一行：`:321-322` 只调用 `_check_for_upload`

### 实测
今日启动日志：
```
[__init__][info]: 恢复处理：2 个未完成产物，已重新派发 0 个任务。
```
那 2 个就是 `断尾人类` 两个停在 `recorded` 的源视频（库里可查）。它们被还原成
`state_dict` 的 `ready` 状态后，**只走了上传判定**——而 `src_video` 没有上传规则，
`_check_for_upload` 自然什么都不做，于是"已重新派发 0 个任务"。

更糟的一条：`dm_video` 若因渲染失败留下 `RECORDED` 记录（`dmrender` 的时长/0 字节检查删掉了产物），
恢复时 `is_recovered_file_usable(path=None/不存在)` 判否 → `_handle_unusable` 直接标 `SKIPPED`（终态）
→ **永远不会再渲染**。`SKIPPED` 不在 `RESUMABLE_STATES` 里。

### 影响
文档里"重启后继续处理未完成的产物（P1 已完成）"只对"已渲染待上传"成立；
"录完待渲染"和"渲染失败"两类都不会自愈，只能人工 `tools/rerender_*.py`。

### 建议修法
把 `onLiveSegment` 里构造 render 消息的那段抽成 `_make_render_msgs(video, segment_idx)`，
在 `resume_recovered` 里对 `src_video` 且 `auto_render` 的分段同样调用；
对"`dm_video` 记录为 RECORDED 但文件不存在"的情况**不要**标 skipped，而应重新渲染（源视频还在）。

## 5. 🟠 P1-3 状态库段号与内存列表下标混用，消息丢失后会错位

### 位置
- 写入用 `segment_id`：`liveevents.py:520`、`:591`
- 写入用**列表下标**：`liveevents.py:832`、`:959`、`:878`、`:908`（`idx + 1`）

### 机理
`state_dict[group_id]` 是**追加式列表**，下标 = 第几个到达 `livesegment` 消息；
状态库 `segment_idx` 用的是下载器的 `video.segment_id`（递增，不因消息丢失回退）。
两者只有在"每条 livesegment 都送达"时才相等。

### 触发条件（生产已出现）
日志里有 `目标任务 'xxx' 不存在（source='downloader', event='livesegment'），消息已丢弃`
与 `Task xxx not exists.`（近 7 天 4 + 1 次）。典型场景：改任务 yml → 热重启任务
（`main.py:267-274`，本次日志出现 1 次）→ 旧下载器的 in-flight 消息被丢弃 →
新任务列表从空开始，而下载器 `segment_id` 继续从 N 递增。

此后 `onRenderEnd` 用 `idx+1`(=1) 去写 `dm_video#1`，会把**第 6 段**的产物记到第 1 段头上；
同一条 `src_video` 又由下载器按 `segment_id=6` 登记过一次 → 同一文件两条记录、指向不同分段。
清理/恢复据此判断会张冠李戴。

### 建议修法
统一以 `video.segment_id` 为准：
```python
idx_key = getattr(info.get('file'), 'segment_id', idx + 1)
```
或把 `state_dict` 改成 `{segment_id: {...}}`（改动更大，属 P2 重构）。

## 6. 🟡 P2 级问题

### P2-1 跳过上传规则被应用到"根本不上传"的源视频槽位
`liveevents.py:672-687` 对**所有** vtype 都跑 `_mark_upload_skipped`，包括 `src_video`。
日志中大量 `src_video 命中跳过上传规则（...）不上传（B站和网盘都跳过）` 属于误报：
源视频本来就没有上传规则。代价是每段多一次 ffprobe（源文件通常几百 MB～GB），
且把 `src_video` 的库状态写成 `SKIPPED`（语义应为 `RECORDED`/`CLEANED`）。
**修法**：只在 `vtype` 出现在 `upload_args` 的 key 中时才评估跳过规则。

### P2-2 `ffmpeg.py:208` 时长解析笔误
```python
h, m, s = int(d.split(':')[0]), int(d.split(':')[0]), float(d.split(':')[2])
#                            ↑ 分用了小时的下标 [0]，应为 [1]
downloaded_duration_ms = h * 3600 + m * 60 + s
```
且变量名叫 `_ms` 实际是秒。该分支只在 `speed<2` 且尚未 stable 时执行一次（通常 time≈00:00:0X，
h=m=0 所以侥幸无害），但一旦首个采样发生在开播 1 小时后，`time_error` 会差出整小时，
直接喂给 `dmw.time_fix()` → 弹幕整体错位。**修法**：改正下标并重命名为 `downloaded_seconds`。

### P2-3 `_check_for_clean(group_id)` 的参数被循环变量遮蔽
```python
def _check_for_clean(self, group_id=None):
    for group_id, video_states in self.state_dict.items():   # 覆盖了形参
```
传进来的 `group_id` 完全无效，每次都全表扫描。`onTaskError` 里循环 `touched_groups` 逐个调用，
等于 O(n²)。功能上不致命，但会让人误以为"只处理该组"。

### P2-4 渲染只有 1 个工作者线程，且 ffmpeg 无超时
`configs/global.yml: render_kernel_args.nrenders: 1`（`Render/__init__.py:34`），
`Render/ffmpeg.py:39` 是 `self.render_proc.wait()`，**没有超时**。
一个卡死的 ffmpeg 会永久占用唯一的渲染线程 → 全部 33 个任务的渲染静默停摆
（日志里只会看到"正在渲染"再也没有下文）。上传同理 `nuploaders: 1`。
**建议**：给渲染加超时看门狗（或至少加"渲染超过 N 小时"告警），并把 `nrenders` 提到 2。

## 7. ⚪ P3 级问题（记录，不急）

1. **`configs/global.yml` 的 `dynamic_config` / `dynamic_config_path` 无人读取**
   `grep` 全仓无引用；代码读的是 `dmr_engine_args.config_path`
   （`DMR/Config/__init__.py:52`）。用户以为关掉 `dynamic_config` 能停热更新，实际不能。
   无副作用（默认值恰好等于 `./configs`），但属误导性配置。
2. **`ReplayTask` 仍强制 `replay/` 前缀**（`replaytask.py:34`），而 `engine._resolve_target()`
   已支持裸任务名路由（`engine.py:54-56`）。经 `engine` 路由进来的裸任务名消息会入队后
   **被任务侧静默丢弃**。当前所有内部发送方都带前缀，所以是潜在缺陷。
3. **`_free_state_memory` 的 `final_status` 与 `w_dmfile: False` 冲突**
   `liveevents.py:915-920`：`auto_clean` 时终态是 `cleaned`，但弹幕版按设计永远停在 `uploaded`
   → 分组只能靠 72 小时超时释放。建议把 `uploaded` 也视为终态（在 `w_dmfile=False` 时）。
4. **`add_event` 先 append 后无条件覆盖**（`replaytask.py:20-23`，已文档化 B7.3）。
   当前 `event_dict` 值都是单个 bound method，所以不触发；一旦有人写 list 就会抛 `TypeError`。
5. **状态库与磁盘存在历史漂移**：8 条 `missing`（库里记录文件不存在，2.44GB）来自
   手工清理工具直接删文件没回写库。不影响运行，但会让"对账统计"失真。
