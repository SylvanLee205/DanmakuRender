# 上游合并与部署记录（2026-10-15）

## 一、为什么合并

上游 `SmallPeaches/DanmakuRender` 在 2026-10-10 提交了 `ab8d3f3`
**"feat: 录制状态持久化与可靠恢复"**，修的正是我们反复手工处理的 4 个问题：

| 上游修复 | 我们之前的对应问题 |
|---|---|
| 消息路由依赖 `replay/` 前缀 → 上传成功却记不上账、清理不触发 | "幻影成功"（云端没文件但记为成功） |
| `_check_for_upload` 空候选 `IndexError` | 上传判断偶发报错 |
| `_check_for_clean` 误置 `cleaned` | 我们手工改过这里 |
| 恢复判定不再依赖 ffprobe（改为文件名标记 + 文件大小） | 孤儿分段（10-07 那次 1.8 GB） |
| 上传前刷新 cookies | 长驻上传器的 cookies 过期 |
| 下载引擎内存优化（管道缓冲、滚动日志、尾部读取） | 长时间运行内存增长 |

**分叉情况**：共同祖先 `4093163`(2026-04-25)；我们独有 46 个提交，上游独有 3 个。
变更规模 **71 文件 / +14805 -398**。冲突 **7 文件 / 22 块**。

### `liveevents.py` 的处理弯路（教训）

```
❌ 第一次：直接采用上游版
   → 丢失 4 个关键功能：
       _notify_live（开播通知）
       PROGRESS（其他文件 import，丢了会 ImportError）
       _get_upload_skip_rule（跳过上传规则）
       onTaskError（修 1.76GB 滞留）

❌ 第二次：以我们的版本为基础
   → 发现上游有 14 个新方法 + 15 处 state_repo 调用点，全在状态恢复链路上
   → 反移植工作量更大

✅ 第三次：以上游为基础 + 移植我们 4 个方法
   → 改 4 处 远少于 改 14 处
   → 另加回上游缺失但我们 7 处在用的 PROGRESS = 25 常量
   → 在 defaultEvent 里挂 _notify_live('start')（上游把 livestart 也走 defaultEvent）
   → 结果 1031 行，两边功能齐全
```

**教训**：解决冲突前先统计"两边各自独有方法的数量"，往少的那边改。

## 四、★ 部署时发现的重大风险（差点造成损失）

部署前检查发现 **`configs/` 是独立目录**（不是 junction 共享），而且：

```
1. prod 有 3 个用户任务配置，dev 完全没有：
     DMR-TG当当.yml        (live.douyin.com/123456789)
     DMR-小玟不是小玫.yml   (live.douyin.com/123456789)
     DMR-灰蒙蒙.yml        (live.douyin.com/123456789)
   → 同步代码时若连带 configs，会删掉这 3 个主播的配置

2. dev 的 global.yml 丢了两个关键段：
     upload_args_task_default  ← 上传规则本体（rclone 命令）
     clean_args                ← 清理配置
   → 这是我合并配置时"以上游为基础"造成的

3. ★ 上传行为被改了：
     prod: realtime: False  ← 整场合并成一个视频再传（用户当前行为）
     dev:  realtime: True   ← 边录边传，会产生一堆碎文件

4. dev 的 YAML 还有合并粘连 bug：
     "...不应该设置太大    retry: 3"（两个语句粘成一行）
```

### 最终部署策略

**只更新代码，`configs/` 保持 prod 原样不动。**

依据：实测 **上游代码完全兼容 prod 的旧配置** —— `Config` 类会从
`default.yml` 自动补齐缺失的键（`state` / `recovery` 等）：

```
✅ prod 配置加载成功
✅ upload_args              dict, 4 键
✅ upload_args_task_default dict, 1 键
✅ clean_args               dict, 4 键
✅ state                    dict, 1 键  ← 自动补上
✅ recovery                 dict, 8 键  ← 自动补上
```

### ⚠️ 部署踩的坑

**问题**：第一次用自写的 Python `shutil.copy2` 脚本同步，结果
`DMR/__init__.py`（状态库注入的关键文件）**静默没被复制**，而且
`DMR/state/__init__.py` 变成了 0 字节，导致：

```
ImportError: cannot import name 'ArtifactKind' from 'DMR.state'
  DMR/Task/liveevents.py line 11: from ..state import (...)
→ DMR 启动即崩溃
```

**根因**：
1. 自写脚本的异常被 `try/except` 吞掉，只打印一行警告，很容易漏看
2. `DMR/__init__.py` 的修改日期一直是 **06-28**，说明从未被碰过 ——
   脚本的文件遍历有 bug（`SKIP_DIRS` 过滤逻辑把顶层目录下的文件漏了）
3. `state/__init__.py` 出现 0 字节的原因未完全查清（疑似复制与
   `__pycache__` 写入竞争）

**修复**：改用 **`robocopy`**（Windows 原生、可靠），并逐文件 MD5 校验。

**教训**：
- **不要自写文件同步脚本**，用 `robocopy`
- 同步后**必须逐文件 MD5 比对**，不能只看"复制了 N 个文件"
- 自写脚本里 `except: print(警告)` 会掩盖真问题

### 新增配置键（自动从 `default.yml` 补齐）

```yaml
state:
  db_path: logs/dmr_state.db      # 状态库路径

recovery:
  on_interrupted_file: ask        # ask/keep/discard 录到一半的产物怎么办
  resume: true                    # 重启后自动继续处理未完成的产物
```

**注意**：
- 状态库是**单一全局库**，以任务名区分。删掉它会丢失所有未完成进度。
- `resume: true`（默认）会把上次没上传/没渲染完的分段接着处理。
  **已上传或已清理的产物永不重跑**，不会重复投稿。
- 若删除了某个任务配置，状态库里还留着它的记录会报
  `StateConsistencyError`，按提示删库或恢复配置。
