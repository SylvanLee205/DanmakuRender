增加启动汇总 + 日志心跳 + 状态检查工具（回答"是否真在监听"）

【用户疑问】
1. "现在还有 [liveevents][info]: XX: 直播开始 这种吗？"
   —— 即：控制台能看到开播消息吗
2. "打开之后没有说那个跟之前一样的 [engine][info]: 下载任务 U 已启动...
    [liveevents][info]: U: 直播已结束... 我不知道真正启动并开始监听主播了没有"

【回答】
1. "直播开始" 走 PROGRESS 级别（liveevents.py L43 defaultEvent），
   **--quiet 下控制台会显示**。而 "直播已结束"（L200 onLiveEnd）是 INFO，
   控制台不显示。
   实测验证：日志里 PROGRESS 标记 0 条，因为重启后还没有主播开播过 ——
   这是正常的，不是坏了。

2. "下载任务 XXX 已启动" 是 engine 的 INFO 消息，属于内部状态，
   控制台**故意**不显示（32 个任务各一行，刷屏）。
   "XX: 直播已结束" 同理不显示。
   所以控制台看起来"什么都没说" —— 但程序确实在监听。

【问题：用户无法区分"正常空闲"和"真卡死"】
控制台降噪后，如果所有主播都没开播，控制台会长时间空白。

【改动 1：启动汇总】
main.py 在 dmr.start() 之后打印：
  ====================================================================
    已加载并开始监听 32 个主播
    每个主播的状态检查结果会写进日志文件；
    控制台只在【开播 / 渲染 / 上传 / 清理】时输出。
    → 所以控制台长时间空白 = 所有主播都没开播，属于正常。
    → 想看每个主播的状态，查日志: logs/DMR-2026xxxx.log
  ====================================================================
（实测 config.replay_config 有 32 个任务）

【改动 2：日志心跳】
main.py 起一个 daemon 线程，每 30 分钟往日志写一行：
  [心跳] 程序运行中，监听 32 个主播。
用 INFO 级别（控制台不显示，避免噪音），只在日志文件留痕。
这样"日志文件还在增长"就有了明确的证据。

【新增 tools/check_dmr_alive.py】
一键检查，回答"到底在不在监听"：
  1. 守护 cmd 进程在不在        （不在 = 崩溃后不会自动重启）
  2. DMR python 进程在不在 + 启动时间 + 内存
  3. 日志最后写入时间            （太久没写 = 可能真卡死）
  4. 心跳行数
  5. 最近的 开播/渲染/上传/清理 活动
  6. CD2 服务状态
  最后给出结论和修复建议。
用法：python tools\check_dmr_alive.py
